# v2.14.0 — ConfigHub reads through the SDK, and `gitops tree`

**Unreleased.** Published baseline is [v2.13.4](v2.13.4.md). This page is
the notes for the next release, cut from `main`.

**What "v2.14" means changed on 2026-10-10.** Until then v2.14 named the whole
adopted P4 scope, and this page was a draft that listed its acceptance gates.
The maintainer decided to publish v2.14.0 now, for the two things below, and
to move those gates to v2.15. Nothing here claims them: six-surface
conformance (#596), controller and workload acceptance, the paired benchmark
(#519, #603) and the remaining P4 issues under
[#645](https://github.com/confighub/cub-scout/issues/645) are open, and are
now the gates before v2.15.0. [The readiness ledger](v2.15-readiness.md) is
where they are tracked.

Two things. cub-scout now reads ConfigHub through the ConfigHub SDK instead of
by starting the `cub` CLI for each read, and checks the session the same way,
so a read-only command no longer needs a `cub` binary for the reads listed
below. And a new command, `gitops tree`, shows what is under each deployer to
any depth.

## New

- **`gitops tree`**: the child Applications of an Argo CD app-of-apps and the
  resources each reports, to any depth, with every deployer's settings and
  state. Built read-only from what each Application reports, with no Argo CD
  API call. `--format ascii|json|md`, and a TUI view.

```bash
cub scout gitops tree                      # as a cub plugin
./cub-scout gitops tree                    # standalone
cub scout gitops tree --format json
./cub-scout gitops tree --format json
```

  Verified on a real Argo CD v3.5.3 in CI. Flux, Sveltos, Helm, Crossplane,
  kro, Modelplane and ConfigHub-delivered trees are not in it yet (#856 to
  #861). There is no MCP tool for it yet (#855).

- **ConfigHub reads through the SDK, by default.** These reads no longer
  start a `cub` process:

  | Read | Used by |
  |---|---|
  | One Unit; a Unit's data; a revision and its data | `compare`, source-truth, the import wizard's checks, attestation evidence in `trace` and receipts |
  | The Units, workers, Targets, ChangeSets, Links, resources, releases and unit events of a space, with `--where` and `--contains`; the same across every space when asked for by `--space '*'` (not releases) | `map`, `status`, `history`, `audit`, `fleet outliers`, `compare bindings`, `gitops status`, `doctor --with-confighub`, and most MCP `confighub_*` tools |
  | Spaces; organizations; a change order by slug; a View by ID; the local cub context | `map`, `views`, `compare three-way --view`, `history changeorder` |
  | The session check every connected command makes first | every connected command |

  The full table, with what is left to `cub`, is in the
  [SDK reader reference](../reference/confighub-sdk-reader.md).

- **`views project` reads a real View.** It now takes the columns from the
  View and each cell from the value ConfigHub evaluated. Before, it read a
  shape `cub` does not print (#852).

## Behaviour changes to expect

- **`cub` is not needed for the reads above.** It is still needed to log in
  (`cub auth login`), for every write (`import` and anything that creates or
  changes something in ConfigHub), and for the reads not yet moved: a list
  with a selection or a stored filter, a View's evaluated columns, an entity
  named by ID, the releases of every space, `unit tree`, `release check` and
  the Kubernetes-shaped reads. A read that needs `cub` on a machine without it
  says so at that read.
- **The way back is one variable.** `CUB_SCOUT_CONFIGHUB_READER=cub` makes
  every read and the session check go through the `cub` CLI, as in v2.13.4.
  Nothing falls back on its own: a failed SDK read is reported as a failure.
- **The session check compares cub-scout's SDK with the server, not your
  `cub`.** `cub` refuses a `cub` that is a minor version older than its
  server. cub-scout now applies that rule to the SDK it was built with
  (v0.8.12, which `cub-scout version` now prints on a second line): a
  ConfigHub server at v0.9 or later is refused, with advice to upgrade
  cub-scout or to read through an up-to-date `cub` with the variable above.
- **Some answers that used to be shown are now errors.** A list the server cut
  short, a list holding entries from another space, a 200 that is not JSON,
  and configuration data whose SHA-256 is not the one ConfigHub reports for
  it. `cub` prints each of these as it came, so for the first, second and
  last the error does not suggest reading through `cub`.
- **A worker's secret is no longer kept by cub-scout.** `cub worker list
  -o json` prints each worker's secret token. When cub-scout lists workers
  through the SDK, it removes that token and the worker's claim token from
  the answer before anything else sees it. No command ever printed them.
- **`map fleet`, `map clusterdata --connected`, `fleet outliers`, `impact`
  and the existing-unit lookup of `import --json`** now ask the same gate as
  every other connected command, so `CUB_SCOUT_OFFLINE=true` and a missing
  session are refused up front (#863). `impact` no longer reports "no
  dependents" when a space's links could not be read.
- **`status` asks ConfigHub nothing when the gate refuses.** With reads
  turned off it used to run `cub auth status` and a worker lookup anyway. It
  now says only what this machine's files say. When the session could not be
  checked (a server error, a timeout) it leaves the session unset; it used to
  say "auth expired".
- **A token that says it has expired is not sent.** The read fails with the
  expiry and `cub auth login`, where the server would have answered a bare
  401.
- **A cub wrapper does not see these reads.** Anything that records or fakes
  `cub` calls sees only what still goes through `cub`.
- **What a Unit looks like follows the SDK cub-scout was built with**, not the
  installed `cub`. A field a newer server adds is absent until cub-scout
  moves to a newer SDK.
- **Go 1.25 to build from source** (`go install`), and the binary is about
  7 MB (9%) larger. The published binaries need neither.

## As measured

On one GitHub-hosted runner with the server in a kind cluster on the same
machine, 15 runs:

| One read of a Unit, milliseconds | min | median | max |
|---|---|---|---|
| `cub unit get` (a `cub` process, start to exit) | 51.4 | 55.8 | 62.7 |
| Through the SDK, space by slug (two requests) | 4.0 | 4.2 | 4.8 |
| Through the SDK, space by ID (one request) | 2.7 | 2.9 | 3.5 |

Most of the `cub` figure is starting a process. Against a server across a
network each request costs both ways of reading more; that was not measured, and
neither was the time for a whole command. **No cost or time saving for an
agent is claimed**: no agent eval was run on this change.

## Limits

- **Unit events were only compared empty.** The test server applies nothing,
  so it has no unit events. That list is shown to be read and to agree with
  `cub` when empty; that an event is printed as `cub` prints it rests on the
  SDK's types and a unit test of the ordering.
- **One server version, plain objects.** Everything was compared on ConfigHub
  v0.8.12 (the version `hub.confighub.com` reported on 2026-10-10), with
  small spaces: no Unit with a Target attached to a worker, no upstream, no
  long list, no change order with a workflow. A hosted server and a
  credential with fewer rights were not tried.
- **No renewal.** A read through the SDK uses the stored token and does not
  renew it.
- **Each request has 30 seconds.** `cub` sets no limit; a very large list can
  time out here and not there.
- **`gitops tree` is Argo CD only**, has no MCP tool, and its eval case does
  not exist yet (#855).

## Opt-in previews also in this build

These first shipped in the v2.13 patch releases, opt-in and not accepted, and
are unchanged here. The docs used to call them "v2.14 candidates"; their
acceptance is part of what moved to v2.15.

- Watch and bot accept strict explicit Kubernetes context selection. One captured
  config feeds inventory, scanner, receipt and optional informer clients; missing
  or blank selections refuse before sink creation, without ambient fallback.
  Defaults and event schemas are unchanged. This selects scope without claiming
  verified cluster identity, total costs or fresh informer observations.

- Opt-in map cluster identity binds inventory and one bounded kube-system
  Namespace read to the same selected config. The separate identity report
  preserves partial/unavailable collection separately from identity verification.
  Context labels do not establish stable identity. Cost fields cover the identity
  reader, not total command cost. CLI/MCP and the loaded TUI identity view share
  this model; unsupported TUI actions are guarded when identity binding is active.
- Opt-in map resource rows retain observed object-instance references and canonical
  merge keys, or explicit identity omissions. Missing UID/scope/type and denied or
  wrong cluster evidence never fall back to names. CLI/MCP and the loaded TUI
  share this evidence without extra reads; legacy/default output is unchanged.
- Watch/bot collection omissions emit `collection.partial` diagnostics. Failed
  resource LISTs preserve a private diff baseline, preventing false deletions or
  rediscovery during denial/recovery. The diagnostic has no object receipt or
  inferred owner. This is inventory coverage, not proof of scanner completeness.
- Recorded ownership pagination limits returned rows while preserving full-scope
  counts and owner totals. Canonical cursors bind exact recording bytes, filters
  and page size. CLI, MCP and loaded TUI pages share the deterministic model.
  The separate page schema preserves default full/summary contracts. This is a
  record limit, not a byte/token budget, input-work limit or savings measurement.
  A separate opt-in report JSON byte budget refuses oversized report data without
  clipping evidence; it excludes display/newline, MCP duplication/protocol/transport,
  input work, tokens and agent cost. A refused TUI page preserves its current state.
- Crossplane lineage refuses ambiguous, foreign and self-parent joins. Known-group
  owner references preserve exact version/type/name and check a supplied UID;
  missing/replaced evidence stays partial with explicit reasons. Label-only joins
  still do not establish UID identity. This correction does not graduate Crossplane
  or implement the complete v2 condition/operation/coverage model.

- Composition trees retain same-name children of a different full reference and
  separate colliding root API references and present/partial observations.
  Unambiguous JSON keys remain unchanged; collision keys are deterministic and
  opaque. This is presentation grouping, not verified cluster/object UID identity.

Offline fixtures, negative controls and host process receipts prepared those
packets. They do not establish current fleet truth, genuine controller
reconciliation, operational advantage or reduced agent spending.

**Configuration investigation continuity.** The [ordered delivery contracts](../reference/configuration-investigation-delivery.md)
include generation provenance (#778), safe Helm inputs (#779), actual permission
profiles (#780), local continuity (#781), exact-release health and standalone
supplied-manifest utility. P4 contract/example checkpoints and implemented runtime
proof remain separate. Connected intent enriches standalone; no new ConfigHub API
or renderer is a release dependency. Full producer adapters and retained storage
have explicit later allocations. No measured advantage is claimed.

## What was and was not verified

Verified before publication:

- required CI on `main` at the tagged commit: Unit Tests, Integration Tests,
  GitOps E2E and Proof Artifact; and a clean local build, `go vet ./...` and
  `go test ./...` on that commit;
- every SDK read against a real ConfigHub v0.8.12 in the Connected E2E lane,
  compared with what `cub` v0.8.12 printed for the same question, byte for
  byte, with the space named by slug and by ID; the recordings are kept under
  `test/fixtures/`;
- the session check and a connected MCP read through the built binary with no
  `cub` on PATH, on that server;
- `gitops tree` on a real Argo CD v3.5.3 in the GitOps E2E lane;
- mutation checks on each slice, each mutation caught by a named test, and an
  independent review of each pull request whose findings are fixed or
  recorded on it.

Not verified, and not claimed:

- anything on a hosted ConfigHub, or with a credential that is not an
  administrator's;
- a ConfigHub server of any other version;
- Full Verification and most of Demo Tests, which still stop at the private
  scanner credential (#774); Windows binaries are not executed;
- any agent eval for these changes.
