# Migrating from cub-scout 2.x to 3.0

This guide lists every breaking change between cub-scout 2.x (`v2.19.0`) and 3.0
and shows the exact before/after commands. The deprecation notices for all
removals shipped in `v2.18.0`, satisfying the one-minor deprecation window
([#595](https://github.com/confighub/cub-scout/issues/595)).

Every removed flag and command fails in 3.0 and names its replacement rather
than being silently ignored.

## 1. Go module path (`/v2` → `/v3`)

If you import cub-scout packages or install from source with `go install`:

| Before (2.x) | After (3.0) |
|---|---|
| `github.com/confighub/cub-scout/v2` | `github.com/confighub/cub-scout/v3` |
| `go install github.com/confighub/cub-scout/v2/cmd/cub-scout@latest` | `go install github.com/confighub/cub-scout/v3/cmd/cub-scout@latest` |

## 2. Plugin-first invocation (`cub scout`)

In 3.0, the `cub` plugin form (`cub scout ...`) is the documented primary form
([#386](https://github.com/confighub/cub-scout/issues/386)). The standalone
`cub-scout` binary remains fully supported with identical commands, flags,
JSON contracts, exit codes, and MCP tools.

## 3. Removed flags and commands

Every command below is shown in plugin form (`cub scout`); standalone
`cub-scout` accepts the exact same arguments.

| Before (2.x) | After (3.0) | Notes |
|---|---|---|
| `cub scout trace deploy/app -n demo --json` | `cub scout trace deploy/app -n demo --format json` | `--json` removed; use `--format json` |
| `cub scout tree --json` | `cub scout tree --format json` | `--json` removed; use `--format json` |
| `cub scout graph export --empty --json` | `cub scout graph export --empty --format json` | `--json` removed; use `--format json` |
| `cub scout gitops status --json` | `cub scout gitops status --format json` | `--json` removed; use `--format json` |
| `cub scout connect --go` | `cub scout connect --map` | `--go` removed; use `--map` (same for `setup connect`) |
| `cub scout app create demo --set-context` | `cub scout app create demo` | `--set-context` removed; pass `--space <name>` to commands that need a space |
| `cub scout hierarchy` | `cub scout map hub` | `hierarchy` removed; use `map hub` or `map --hub` |
| `cub scout fleet outliers` | *(none — removed)* | See [Why `fleet outliers` was removed](#why-fleet-outliers-was-removed) |

## 4. Verdict words leave `compare source-truth` JSON and MCP output

In 2.x, `compare source-truth --format json` and the `compare_source_truth` MCP
tool emitted `status` (`PASS`, `WATCH`, `ASK`, `BLOCK`) and `source_truth`
(`AGREED`, `MISMATCH`, `INCOMPLETE`, `BLOCKED`, `UNKNOWN`).

In 3.0, those verdict fields are removed from JSON and MCP output and remain
only in ASCII and Markdown output for human readers (maintainer's decision,
2026-11-16). Machine readers use `answer.state` and `answer.reason`:

| Before (2.x JSON / MCP) | After (3.0 JSON / MCP) |
|---|---|
| `.status == "PASS"` / `.source_truth == "AGREED"` | `.answer.state == "agreed"` (plus `.answer.reason`) |
| `.status == "BLOCK"` / `.source_truth == "MISMATCH"` | `.answer.state == "not-agreed"` |
| `.status == "WATCH"` / `.source_truth == "INCOMPLETE"` | `.answer.state == "incomplete"` |
| `.status == "ASK"` or `BLOCKED` (read failed) | `.answer.state == "not-observable"` |

Immutable `receipt/v1` artifacts (`receipt verify`) are unchanged.

## 5. Why `fleet outliers` was removed

`fleet outliers` compared unit and target slugs within a single ConfigHub space,
which could not establish cross-cluster lineage across spaces
([#562](https://github.com/confighub/cub-scout/issues/562)). There is no direct
replacement in 3.0; `cub scout map fleet` provides connected inventory without
claiming cross-cluster outlier equivalence.

## 6. `cub` CLI version floor

Connected commands check compatibility with `cub` and ConfigHub through the
connected gate (`docs/reference/cli-contract.md`). The exact 3.0 `cub` version
floor is set at `v3.0.0` release time against the then-current `cub` release
(currently `v0.11.x`).
