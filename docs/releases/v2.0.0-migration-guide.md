# v2.0.0 Migration Guide: `cub-scout` to `cub scout`

> **Status:** Migration guide for the `v2.0.0` plugin switchover. Plugin-form support has landed in `main` (plugin mode detection, auth inheritance, cobra help/command-path adjustments, parity test). The final missing piece is the `v2.0.0` release asset that ships the plugin-compatible archive via `.goreleaser.yaml`.
> Canonical plan: [`v2.0.0-plugin-plan.md`](v2.0.0-plugin-plan.md).
> Boundary doc: [`cub vs cub scout`](../concepts/cub-vs-cub-scout.md).
> Plugin install how-to: [`plugin-install.md`](../howto/plugin-install.md).

## What Is Changing

In `v2.0.0`, `cub-scout` becomes the first official `cub` plugin.

The preferred invocation changes from:

```bash
cub-scout doctor
cub-scout explain deploy/frontend -n default
cub-scout compare three-way --scope deploy/frontend -n default
cub-scout mcp serve
```

to:

```bash
cub scout doctor
cub scout explain deploy/frontend -n default
cub scout compare three-way --scope deploy/frontend -n default
cub scout mcp serve
```

Everything after the first word is unchanged. Flags, JSON contracts, exit codes, and MCP tool names remain identical.

## What Is Not Changing

- The `cub-scout` binary continues to ship as a standalone release. Nothing forces you to install `cub` or use the plugin form.
- Every existing command, flag, and JSON contract is preserved under the plugin form. The plugin is the same binary exec'd by `cub`, not a reimplementation.
- Read-only default. Plugin form does not add any mutation surface.
- ConfigHub authority boundary. `cub scout` never becomes an apply/mutation path.

## Why the Switchover

The product story is clearer under one family:

- `cub` is the authority and governed execution host.
- `cub scout` is the explorer, proof, and investigation plugin.
- `cub scout mcp serve` is the AI investigation gateway.

A single `cub plugin install` removes the "which binary, which brew tap, which install guide" friction that had accumulated around standalone `cub-scout`.

See [`cub vs cub scout`](../concepts/cub-vs-cub-scout.md) for the full family boundary.

## Transition Policy

During the `v2.x` line:

- **Both `cub scout ...` and `cub-scout ...` are supported.** The plugin form is preferred in docs, prompts, and AI guidance.
- **Standalone `cub-scout` remains a first-class release artifact.** Homebrew, krew, tar.gz, and source builds keep working.
- **Nothing is removed.** There is no deprecation warning, no feature drop, no exit-code change.

After `v2.x` the standalone support policy is revisited. No decision has been made to sunset standalone `cub-scout`.

## Step-by-Step Migration

### 1. Decide which form you want

Use the plugin form (`cub scout ...`) if:

- you already install or plan to install `cub` for ConfigHub workflows
- you want one unified CLI family
- you are wiring AI tools, slash commands, or agent instructions (cleaner product story)

Keep the standalone form (`cub-scout ...`) if:

- you only need read-only Kubernetes observation and do not use ConfigHub
- you have existing CI pipelines, scripts, or demos pinned to `cub-scout`
- you prefer a single binary with no host dependency

Both forms will work during `v2.x`. You can migrate incrementally.

### 2. Install `cub` (plugin form only)

If you already have `cub` installed, skip this step.

See the upstream `cub` install docs in the [`confighub/sdk`](https://github.com/confighub/sdk) repo.

### 3. Install the `cub scout` plugin (plugin form only)

```bash
cub plugin install confighub/cub-scout
```

`cub` will fetch the latest `cub-scout` GitHub release, match the archive for your OS and architecture, and install it as the `scout` plugin.

Verify:

```bash
cub scout version
cub scout doctor --help
```

See the full [plugin install how-to](../howto/plugin-install.md) for pinned versions, offline install, and troubleshooting.

### 4. Update scripts, CI, and docs

The mechanical change is a prefix flip:

```diff
- cub-scout doctor
+ cub scout doctor

- cub-scout compare three-way --scope cluster --format json
+ cub scout compare three-way --scope cluster --format json

- cub-scout mcp serve
+ cub scout mcp serve
```

No flag or argument changes. Search-and-replace on `cub-scout ` → `cub scout ` is a safe starting point for shell scripts and Markdown documentation.

### 5. Update AI tooling, slash commands, and agent prompts

For AI tools that reference cub-scout:

- Update MCP server configs from `cub-scout mcp serve` to `cub scout mcp serve`.
- Update slash commands and Claude Code skill files to reference `cub scout ...`.
- Update prompt templates and `AI-README-FIRST.md`-style docs in your own repos.

The MCP tool names themselves (`doctor`, `explain`, `trace`, `map`, `scan`, `compare_three_way`, `confighub_units`, `confighub_unit_get`, `confighub_changesets`) are unchanged.

### 6. Verify parity

Run both forms against the same cluster and scope:

```bash
cub-scout doctor --format json > /tmp/standalone.json
cub scout doctor --format json  > /tmp/plugin.json
diff /tmp/standalone.json /tmp/plugin.json
```

They should match. If they diverge, file a parity bug with the `cub-scout` repo.

## FAQ

**Q: Do I have to install `cub` to keep using cub-scout?**
No. Standalone `cub-scout` is fully supported. The plugin form is an additional option, not a replacement.

**Q: Does the plugin form change what cub-scout can do?**
No. It is the same binary executed by `cub` instead of directly. Every command, flag, JSON contract, exit code, and MCP tool is identical.

**Q: Can I switch back and forth?**
Yes. Both forms can coexist on the same machine. They are the same binary; only the invocation path differs.

**Q: Does the plugin form share auth with cub?**
Yes. When `cub` invokes the plugin, it passes `CUB_TOKEN`, `CUB_SERVER`, `CUB_CONTEXT`, and `CUB_SPACE` environment variables. Connected `cub scout` commands inherit `cub`'s active context without a separate login.

**Q: What if I have both `cub-scout` on `$PATH` and the plugin installed?**
They are independent. `cub-scout doctor` runs the standalone binary. `cub scout doctor` runs the plugin-installed binary under `$CUB_CONFIG/plugins/scout/`. They do not conflict.

**Q: Does my existing MCP client config still work?**
Yes, as long as it references `cub-scout mcp serve`. Updating to `cub scout mcp serve` is preferred but not required during `v2.x`.

**Q: Are there any flag or JSON changes in `v2.0.0`?**
No. `v2.0.0` is a packaging and positioning milestone, not a CLI contract change.
