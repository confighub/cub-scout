# v2.0.0 Release Notes — `cub-scout` Becomes `cub scout`

> **Status:** Draft release notes. This file describes what the `v2.0.0` tag will ship when cut from `main`. It is kept in the repo so reviewers can see the release story in the same diff as the code and test changes that enable it.
> **Previous milestone:** [`v1.13.0`](v1.13.0.md) — trust-surface work for connected proof and revision-aware hints.
> **Canonical plan:** [`v2.0.0-plugin-plan.md`](v2.0.0-plugin-plan.md).

**Theme:** *`cub-scout` becomes the first official `cub` plugin.*

This is a **packaging, boundary, and polish release**, not a feature release. Every command, flag, JSON contract, exit code, and MCP tool name is unchanged from `v1.13.x`. The change is how the tool is invoked and how it fits alongside `cub`:

- **`cub scout`** is the preferred invocation form, installed via `cub plugin install confighub/cub-scout`
- **`cub scout mcp serve`** is the preferred AI investigation gateway
- **`cub-scout`** standalone remains fully supported during the `v2.x` transition — nothing is removed or deprecated

---

## What's New

### First-class `cub` plugin support

```bash
cub plugin install confighub/cub-scout
cub scout doctor
cub scout explain deploy/frontend -n default
cub scout compare three-way --scope cluster
cub scout mcp serve
```

The plugin form inherits auth and context from the parent `cub` process automatically. No separate `cub-scout auth login` step is needed — if the host `cub` is logged in, `cub scout` connected features work immediately.

Under the hood:

- **`CUB_PLUGIN=1` detection** — `pkg/hub/plugin_mode.go` exposes `IsPluginMode`, `PluginToken`, `PluginServer`, `PluginContext`, and `PluginSpace` for the rest of the code to key off.
- **Auth inheritance without recursion** — `pkg/hub/auth.go` and `cmd/cub-scout/status.go` honour `CUB_TOKEN` from the environment when running as a plugin, avoiding the wasteful (and recursive) `cub auth get-token` shell-out that would otherwise re-enter `cub` on every `CurrentMode()` check.
- **Cobra help / command-path rendering** — plugin-mode usage and help templates render `cub scout <subcmd>` consistently across the entire command tree. Subcommand help no longer drops the `scout` token.
- **Hint rendering** — `TRY NEXT:` and `nextSteps[].nextCommand` output now emits `cub scout ...` in plugin form and keeps `cub-scout ...` in standalone form, so hints match however the user invoked the tool.

### New `cub scout` release asset

`.goreleaser.yaml` adds a `cub-scout-plugin` build that compiles the same source as a binary named `main` and ships it inside the default per-OS/arch archive alongside `cub-scout` and `kubectl-cub_scout`. One archive per platform now serves direct download, Homebrew, krew, AND `cub plugin install confighub/cub-scout` without asset-ordering concerns.

Windows is excluded from the plugin build because `cub`'s plugin invocation path relies on `syscall.Exec`, which does not exist on Windows. Standalone `cub-scout` on Windows is unaffected.

### Family boundary, finalized

`cub scout` is for **observation, explanation, comparison, troubleshooting, proof, and AI investigation routing**.

`cub scout` is not for **approvals, governed execution ownership, apply/mutate control-plane authority, or replacing provider-owned action surfaces**. Those stay with `cub`.

The authoritative boundary document is [`docs/concepts/cub-vs-cub-scout.md`](../concepts/cub-vs-cub-scout.md), with a complete version matrix in [`docs/reference/host-plugin-compatibility.md`](../reference/host-plugin-compatibility.md).

### Release-gate parity test

`cmd/cub-scout/plugin_parity_test.go` builds the binary once, stages it under both `cub-scout` (standalone) and `main` (plugin) layouts, runs 15 representative cases against each, and confirms the output matches modulo a small documented set of benign differences:

- 9 offline help subtrees (`doctor`, `explain`, `trace`, `map`, `scan`, `compare three-way`, `mcp serve`, `history`, `fleet`, `import`, `gitops`)
- 1 offline deterministic JSON output path (`scan --file --json`)
- 1 end-to-end connected-command offline-mode error (`history deploy/... --format json` under `CUB_SCOUT_OFFLINE=true`)

The test runs on every `go test ./cmd/cub-scout/` invocation and will immediately catch any new command that accidentally diverges between the two invocation forms. The single release-gate invariant the v2.0 plugin plan depends on is now enforced in CI.

### Structured-content layer, split out of `mcp.go`

`cmd/cub-scout/mcp.go` dropped from ~1170 to ~760 lines; the extraction and hint-assembly helpers now live in `cmd/cub-scout/mcp_structured.go`. Behavior is unchanged. Pure refactor that isolates the "what does this tool's JSON output get wrapped into" layer from the request/response plumbing, so adding a new structured-output tool is a single helper + a case in `buildMCPStructuredContent`.

## Migration

Existing `cub-scout ...` invocations continue to work unchanged. There is **no deprecation warning, no exit-code change, no feature drop**. Migration is a search-and-replace from `cub-scout ` to `cub scout ` in shell scripts, CI pipelines, AI tool configs, MCP client setups, and documentation. See [`v2.0.0-migration-guide.md`](v2.0.0-migration-guide.md) for the step-by-step path.

Both invocation forms can coexist on the same machine. They are the same binary; only the invocation prefix differs.

---

## What's Not Changing

- **CLI commands, flags, arguments, exit codes.** The `TestPluginParity_StandaloneMatchesPlugin` test enforces this.
- **JSON contracts.** `--format json` and `--json` output is byte-identical across forms for the same cluster state.
- **MCP tool set and tool names.** `doctor`, `explain`, `trace`, `map`, `scan`, `compare_three_way`, `confighub_units`, `confighub_unit_get`, `confighub_changesets` keep the same identities and descriptions.
- **Read-only default.** `cub scout` never writes to the cluster. Connected features write to ConfigHub, not manifests.
- **Standalone `cub-scout`.** Homebrew, krew, tar.gz, source build all continue to work identically. No forced migration.

## Upgrade / Install

### Plugin form (preferred)

```bash
cub plugin install confighub/cub-scout
cub scout version      # verify
cub scout doctor       # first command
```

### Standalone form (unchanged)

```bash
# Homebrew
brew install confighub/tap/cub-scout

# krew
kubectl krew install cub-scout

# direct
curl -L https://github.com/confighub/cub-scout/releases/download/v2.0.0/cub-scout_v2.0.0_darwin_arm64.tar.gz | tar xz
./cub-scout doctor
```

## Known Limitations

- **Non-hint legacy strings still emit `cub-scout`.** Error-recovery messages, root landing page copy, and baked-in `Long` descriptions continue to reference `cub-scout` literally even in plugin mode. These are cosmetic; standalone form is still the documented primary form during `v2.x`, and the shell scripts in those strings remain valid copy-paste targets. Future polish will extend `preferInvocationForm` to these sites.
- **Windows plugin form not supported.** `cub`'s plugin dispatch uses `syscall.Exec`. Standalone `cub-scout` on Windows is unaffected.
- **Connected smoke test against live ConfigHub is manual.** The parity test validates behavior under forced offline mode and against help output; full end-to-end connected-plugin testing requires a logged-in `cub` host and is part of the release-candidate smoke-test procedure, not automated CI.
