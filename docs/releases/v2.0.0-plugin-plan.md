## Why This Milestone Exists

`cub-scout` has reached the point where the main value is no longer basic diagnosis.

Its strongest value is now:

- trustworthy proof
- cross-system investigation
- connected read paths
- AI/MCP-friendly evidence and workflow guidance

That makes `cub-scout` a strong candidate to become the **first official `cub` plugin**.

The goal of `v2.0.0` is not only to change packaging.

The goal is to make the product boundary and the AI/MCP story clearer:

- `cub` is the authority and governed execution host
- `cub scout` is the explorer, proof, and investigation plugin
- `cub scout mcp serve` is the AI investigation gateway for ConfigHub-connected reality and related provider ecosystems

## 2.0 Positioning

### One-Sentence Positioning

`cub scout` is the explorer plugin for `cub`, and its MCP gateway is the AI front door for cross-system investigation and proof across ConfigHub, Kubernetes, Argo CD, Flux, and related platforms.

### Short Product Paragraph

`v2.0.0` makes `cub-scout` the first official `cub` plugin under the `cub scout` namespace. The plugin remains read-first and evidence-first: it helps operators and AI assistants explore, explain, compare, trace, and prove what is happening across live systems and ConfigHub-connected context. Its MCP gateway is the investigation front door for AI workflows, coordinating evidence across ConfigHub, Kubernetes, Argo CD, Flux, and other domain-aware provider surfaces without becoming the mutation or control-plane authority.

### Boundary Statement

`cub scout` is for:

- observation
- explanation
- comparison
- troubleshooting
- proof
- AI investigation routing

`cub scout` is not for:

- approvals
- governed execution ownership
- apply / mutate control-plane authority
- replacing provider-owned action surfaces

## MCP Wording for 2.0

### Primary MCP Positioning

`cub scout mcp serve` is the explorer and investigation gateway.

It understands ConfigHub-connected reality and can coordinate with domain-aware AI/MCP gateways or provider packs for Kubernetes, Argo CD, Flux, and more.

It helps the AI gather and normalize evidence across systems, while authority and mutation stay with `cub` and the owning provider surfaces.

### What It Is

`cub scout mcp serve` should be documented as:

- the MCP front door for understanding and proving ConfigHub-connected reality
- the read-first AI investigation gateway
- the evidence coordinator across live systems and connected context
- the routing and explanation layer for troubleshooting workflows

### What It Is Not

`cub scout mcp serve` should not be documented as:

- the full ConfigHub API over MCP
- the approval or apply gateway
- the control plane
- the mutation owner for ConfigHub or provider systems

## Product Decisions to Lock Before Implementation

These must be treated as explicit `v2.0.0` decisions, not accidental consequences:

1. `cub scout` becomes the preferred invocation.
2. `cub-scout` remains supported during the transition line.
3. `cub-scout` is one plugin namespace, not many separate plugins.
4. `cub scout mcp serve` becomes the preferred MCP path.
5. `cub` remains the host for governed execution and authority-bearing provider packs.
6. Pluginization must strengthen the family boundary, not blur it.

## Command Shape

The canonical plugin surface should preserve the current product shape:

```bash
cub scout doctor
cub scout explain
cub scout trace
cub scout compare three-way
cub scout map workloads
cub scout map issues
cub scout scan
cub scout mcp serve
```

Transition rule:

- `cub-scout ...` remains valid during the transition window
- `cub scout ...` becomes the preferred documented form

## Milestones to `v2.0.0`

### M0 — Decision Lock and Product Boundary

**Theme:** Freeze the meaning of the switchover before packaging work begins.

Must land:

- this Plugin Plan
- final positioning statement for `cub scout`
- final MCP boundary statement
- decision that `cub scout` is the preferred invocation
- support policy draft for standalone `cub-scout`

Exit criteria:

- docs use one consistent boundary story
- maintainers agree that `cub scout` is not a control-plane move

### M1 — Plugin Packaging and Host Parity

**Theme:** Make plugin installation and invocation real.

Must land:

- `cub plugin install confighub/cub-scout` path
- release asset naming compatible with the `cub` plugin installer
- working `cub scout ...` command dispatch
- plugin-aware help/discovery in `cub`

Parity must be verified for:

- `doctor`
- `explain`
- `trace`
- `compare three-way`
- `map workloads`
- `map issues`
- `scan`
- `mcp serve --help`

Exit criteria:

- `cub scout ...` and `cub-scout ...` are behavior-identical for the core surfaces
- plugin install works from real release assets

### M2 — Trust and Proof Polish

**Theme:** Make the switchover feel like a graduation, not just a rename.

High-value work:

- rollout-in-progress caveats
- clearer observed vs connected vs inferred framing
- structured caveats in JSON/MCP where needed
- stronger closeout and receipt surfaces
- no optimistic success claim without explicit proof

Exit criteria:

- no major known trust gap remains in the primary troubleshooting path
- the main repeat-run flow does not depend on hidden interpretation tricks

### M3 — AI/MCP Gateway Readiness

**Theme:** Make `cub scout` the investigation front door for AI.

Must land:

- crisp MCP tool identity and descriptions
- capability/mode clarity where useful
- structured next steps and caveats on the highest-value surfaces
- thin-adapter direction for `cmd/cub-scout/mcp.go`
- docs that say `cub scout mcp serve` is the preferred explorer gateway

Important scope rule:

- this milestone does **not** require full gateway-core extraction
- it does require enough structure that pluginization and future provider coordination stay clean

Exit criteria:

- the MCP path is clearly documented and trustworthy
- the plugin story and MCP story reinforce each other

### M4 — Docs, Migration, and Support Policy

**Theme:** Make the family understandable in one read.

Must land:

- migration guide: `cub-scout ...` -> `cub scout ...`
- boundary doc: `cub` vs `cub scout`
- plugin install docs
- MCP docs updated for the 2.0 story
- AI-facing docs updated to prefer `cub scout`
- compatibility/support matrix for host/plugin combinations

Exit criteria:

- a new user can understand the family split quickly
- an AI assistant can choose `cub scout` without guessing

### M5 — Release Gate and Switchover

**Theme:** Ship only when the plugin story is boringly real.

Release gate:

- plugin install works from published assets
- parity tests pass
- `go test ./...` passes
- `cub --help` makes `scout` discoverable
- migration docs are live
- MCP docs are live
- Homebrew/release story is settled

Release outcome:

- `v2.0.0` becomes the official switchover to `cub scout`
- standalone `cub-scout` remains supported for the transition period

## Non-Goals for `v2.0.0`

These are important, but they should not block the plugin switchover:

- full AI gateway-core extraction
- full provider-pack architecture across the whole family
- turning `cub-scout` into the mutation host
- adding a large batch of new explorer commands purely for the release

## Practical Success Test

`v2.0.0` is successful if this feels natural:

```bash
cub plugin install confighub/cub-scout
cub scout doctor
cub scout explain deploy/frontend -n default
cub scout compare three-way --scope deploy/frontend -n default --format json
cub scout mcp serve
```

and users can understand, without hand-holding:

- why they should start with `cub scout`
- why `cub scout` is read-first
- why `cub` still owns authority and mutation
