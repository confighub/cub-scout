# v2.19.0 — Flux "not yet" is WATCH, and release check runs on a real cluster

**Published on 2026-11-19** from commit `bcf38522` by Release run 44576146102;
see [Publication checks](#publication-checks). The release before it is
[v2.18.0](v2.18.0.md).

One behaviour change: `release check` under Flux now says "not yet" when the
Flux source and Kustomization are on another revision, as it already did for
Argo CD. The rest is proof. `release check`, the one command whose v2.18.0
answer had no real-cluster check, now has one. And under Flux and Argo CD,
each comparison of a deploying tool's recorded live status with the cluster
has been seen to agree and to disagree on a real cluster.

Read [Behaviour changes to expect](#behaviour-changes-to-expect) before
upgrading if you gate on `release check --fail-on` for Flux.

## Changed

- **`release check` under Flux: another revision is `WATCH`**
  ([#982](https://github.com/confighub/cub-scout/pull/982), the maintainer's
  decision of 2026-11-19).
  - Before, the Flux adapter required the OCIRepository to report the
    expected artifact, so a source on another revision made the controller
    stage `INCONCLUSIVE`, and the answer `not-observable` /
    `evidence-incomplete`. Flux's evidence was there, and said "another
    revision".
  - Now, when every other binding check passes and both the OCIRepository
    and the Kustomization report another revision, the controller stage is
    `WATCH` ("Controller reports a different bundle revision: …"), and the
    answer `not-compared` / `controller-reports-other-revision`. That is
    what an Argo CD Application on another revision already gave.
  - A source on another artifact while the Kustomization still reports the
    expected bundle stays `INCONCLUSIVE`: the two are mid-transition, and
    nothing is established.

## Behaviour changes to expect

- **`release check --fail-on INCONCLUSIVE` no longer fires** for a Flux
  source and Kustomization on another revision; `--fail-on WATCH` or
  `any-non-pass` does. The JSON `verdict` is `WATCH` there, and
  `answer.state` is `not-compared`. The Flux rule is in the release check
  answer table of
  [json-contracts.md](../reference/json-contracts.md#release-check-answer-since-v218).

## What was and was not verified

- **`release check` on a real cluster**
  ([#979](https://github.com/confighub/cub-scout/pull/979)). v2.18.0 shipped
  its answer without one, since no lane ran it. The GitOps lane now pushes a
  literal bundle to a local registry on the kind cluster, lets Flux deliver
  it, and runs `release check`. The delivered bundle gives `PASS` /
  `matches`. A bundle Flux was not pointed at, holding the same objects
  under another revision, gives `WATCH` / `not-compared` (GitOps run
  44558934885); before #982 it gave `INCONCLUSIVE`. With this, each of the
  seven commands that gained an answer in v2.18.0 has its answer checked on
  a real cluster, though not in every state: `release check`'s `differs`
  and `not-observable`, and `release check` under Argo CD, are not run on
  one.
- **A recorded live status found untrue, on a real cluster**
  ([#980](https://github.com/confighub/cub-scout/pull/980),
  [#984](https://github.com/confighub/cub-scout/pull/984); refs
  [#887](https://github.com/confighub/cub-scout/issues/887)). The live-status
  lane writes untrue statuses on a Release the way argobot writes its own,
  and reads them back with `gitops status --with-confighub`. Under Flux and
  Argo CD:
  - `OutOfSync` while the controller reports the Release's digest:
    `clusterCheck.state` is `disagrees`;
  - `Healthy` while the listed workload is down (its node cordoned and its
    pods deleted, which neither controller undoes): health is `disagrees`;
  - `Degraded` while every listed workload is ready: health is
    `not-observable`, not a disagreement, since the report may concern a kind
    cub-scout does not read.

  These checks change no cub-scout code. They show on a real cluster the
  comparison v2.15 shipped.
- **CI pins.** Argo CD v3.6.2 in the GitOps, demo, attach and full lanes
  ([#978](https://github.com/confighub/cub-scout/pull/978)). kind v0.33.0 and
  `kindest/node:v1.35.8`, by digest, in every kind step
  ([#983](https://github.com/confighub/cub-scout/pull/983)). The Kubernetes
  minor is unchanged, so the skew from the client libraries is too. Every lane
  with a kind step passed on the new pins before the merge, except the full
  lane, which was not run.
- **Tests that fail without the change.** #982 adds a test of both Flux cases
  through the answer, and a row in the negative-evidence matrix; removing the
  new branch fails both.
- **Not seen on a real cluster:** a StatefulSet or DaemonSet in the
  live-status comparison (the lane's Release delivers only a Deployment);
  any Sveltos comparison, since Sveltos reports no digest and is never
  compared; and a hosted ConfigHub server.
- **Not measured:** no paid eval run was made.
