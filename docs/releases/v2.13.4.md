# v2.13.4 — `gitops settings` for agents: an MCP tool and a compact view

**Not published.** These notes describe the release that will be cut from
`main`; this line is replaced when the tag is published.

A small additive release on top of v2.13.3. It makes `gitops settings`
available to agents over MCP and adds a compact JSON view. One filter changes
meaning; see [Behaviour changes](#behaviour-changes-to-expect).

## New

- **MCP tool `gitops_settings`.** The `gitops settings` report over
  `cub-scout mcp serve`, with `setting`, `project`, `namespace`, `context` and
  `view` arguments. A filter that is misspelt, wrong-typed or empty is refused,
  not dropped.
- **`gitops settings --view`** (JSON only): `all` (the default, as before),
  `summary`, `groups`, `settings` or `deployers`. Every view keeps the scope,
  counts, reads and link sources that say whether it is complete.
- **A compact `summary` view**, which is what the MCP tool returns unless asked
  otherwise: per Argo CD project or Flux namespace, `policies` and `options`
  map each setting to its values and each value to the deployers that have it,
  as `namespace/name`, with `unset` marking the ones counted under a controller
  default. It is written on one line.

```bash
cub scout gitops settings --format json --view summary       # as a cub plugin
./cub-scout gitops settings --format json --view summary     # standalone
```

`gitops settings` remains a preview: the JSON shapes may still change.

## What an agent gets from it, as measured

Three eval cases ask one question: which Argo CD Applications sync
automatically without self-heal, and which Flux objects are suspended? Three
runs per arm ([report](../../evals/reports/2026-10-09-gitops-settings.md)).

| Situation | Result |
|---|---|
| The agent already has the raw `kubectl` export on disk (30 or 300 deployers) | It never called the tool. No benefit, and on the small case the cub-scout arm cost about a third more for the same answer |
| The agent has cub-scout and no export (300 deployers) | Correct in all runs, in 4 turns and about 19 seconds, at $0.21 a run, against a median $0.41 and a mean $0.84 for an agent reading the export |

This is one question on generated objects with no controllers running, three
runs per arm, one model. The second row compares arms that hold different
evidence, and its baseline read a prepared export; an agent running `kubectl`
itself was not measured. **No general cost or time saving is claimed.**

## Behaviour changes to expect

- `gitops settings --setting <name>` with no value now selects deployers whose
  spec **declares** that setting. In v2.13.3 it also matched a policy that was
  left unset or did not apply, so `--setting self-heal` matched every
  Application.
- Nothing else in v2.13.3's output changes. `--format json` without `--view` is
  the same document.

## Limits

- The tool lists an Application by what its spec declares, whichever namespace
  it is in. It does not check whether an Argo CD instance is configured to
  manage Applications in that namespace.
- The plugin's skills do not mention `gitops_settings`; an agent finds it in
  the MCP tool list. The frozen agent benchmark pins the skills tree, and
  re-pinning it is a separate decision.
- Declared settings only: no verdict, and nothing about whether a controller
  acted. Sveltos, AppProject-imposed settings and per-resource annotations are
  not covered ([#839](https://github.com/confighub/cub-scout/issues/839)).

## What was and was not verified

Verified before publication:

- required CI on `main`: Unit Tests, Integration Tests, GitOps E2E and Proof
  Artifact; and a clean local build, `go vet ./...` and `go test ./...`;
- deterministic tests for the views, the summary (held to the same content as
  the verbose view), flag validation and the MCP tool, with 18 mutation checks,
  each caught by a named test;
- the eval recorders run the real `cub-scout mcp serve` against a kind cluster
  with the real Argo CD v3.5.3 and Flux CRDs and assert its answers;
- an independent review, which recomputed the report's figures from the raw
  result files and whose findings are fixed in this release.

Not verified, and not claimed:

- The MCP tool was not run against a cluster with running Argo CD or Flux
  controllers; the eval scenarios are CRDs and objects only. The CLI it wraps
  was, for v2.13.3.
- Full Verification and most of Demo Tests still stop at the private scanner
  credential (#774). Windows binaries are not executed.
- Nine other eval case files fail to load with the current Claude Code version
  ([#844](https://github.com/confighub/cub-scout/issues/844)); they are
  unrelated to this release and were not run.
