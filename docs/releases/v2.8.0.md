# v2.8.0 Release Notes — ConfigHub Delivery Evidence and Bot Mode

> **Status:** Draft release candidate.
> **Previous release:** [`v2.7.0`](v2.7.0.md) — live delivery observability.

**Theme:** answer "what happened?", "is it fresh?", and "can I move on?" with
bounded ConfigHub evidence, and make the five run modes explicit while keeping
cub-scout read-only.

This release is additive. It does not change cub-scout's read-only boundary,
existing JSON fields, or exit-code contract.

## Highlights

### Bounded ConfigHub evidence on `gitops status`

`gitops status` now supports:

```bash
./cub-scout gitops status \
  --with-confighub \
  --confighub-space prod \
  --confighub-since 24h \
  --format json
```

The new `deliveryEvidence` JSON envelope includes:

- ConfigHub live-status writeback from `confighub.com/live-status`
- release history from `cub release list`
- unit-event history from `cub unit-event list`
- conservative in-cluster event-consumer Deployment health
- structured omissions for missing, stale, malformed, disconnected, or
  RBAC-blocked evidence

Reads are scoped to the current cub space by default, can use
`--confighub-space '*'` only when explicitly requested, and are bounded by
`--confighub-since`. The command does not consume event cursors.

### Delivery and application health stay separate

Live-status parsing emits both:

- `deliveryVerdict` from sync/operation state
- `applicationHealthVerdict` from reported health state

Stale successful observations downgrade to `WATCH`. Missing evidence remains
`INCONCLUSIVE`. Delivery controllers and Kubernetes remain the status
authorities; cub-scout only reports evidence.

### Object-correlated delivery evidence on trace and explain

`trace` and `explain` now support the same bounded evidence controls:

```bash
./cub-scout trace deploy/api -n prod --with-confighub --format json
./cub-scout explain deploy/api -n prod --with-confighub --format json
```

These commands attach `deliveryEvidence` only when exact identifiers support the
join. Live-status writeback requires exact space plus Argo Application name or
ConfigHub unit slug. Release evidence requires exact space plus target. Unit
events require exact unit ID, or unit slug plus space. Missing labels, missing
space, non-matching rows, absent event consumers, disconnected ConfigHub, and
RBAC/list failures become structured omissions.

### Controller-family coverage is explicit

`gitops status --format json` now includes `controllerCoverage[]`, and ASCII /
Markdown render the same facts. The coverage ledger records Flux, Argo CD,
ConfigHub, Sveltos, and Modelplane as `found`, `not_found`, `partial`, or
`unreadable`, including checked kinds, observed kinds, object counts, and
structured list omissions. This is the release's main API-load-aware honesty
upgrade: missing CRDs stay quiet, while RBAC/API failures are preserved for
operators, plugins, MCP callers, and bots.

### Modelplane-on-Crossplane trace evidence

Direct Modelplane traces now preserve Modelplane as the higher-level owner while
surfacing Crossplane composition substrate evidence when present:
`crossplane.io/composite`, `crossplane.io/claim-*`,
`crossplane.io/composition-resource-name`, and verified Crossplane field-manager
strings. This is a conservative trace/explorer parity step; deeper object-level
joins across every Crossplane layer remain follow-up work.

### MCP GitOps and connected parity

Standalone MCP mode now includes `gitops_status`, a read-only wrapper for
`gitops status --format json`, so agents can ask delivery-health and
controller-coverage questions without freehand shelling.

Connected MCP mode adds read-only tools for the same evidence:

- `confighub_live_status`
- `confighub_releases`
- `confighub_unit_events`

`compare_source_truth` now derives its strategy enum from the same registry as
the CLI, closing the previous MCP/CLI strategy drift.

### Five run modes and bot mode

The README now opens with the five supported ways to run cub-scout:

- standalone client
- ConfigHub plugin
- MCP server
- watch stream
- in-cluster bot

`cub-scout bot` is a first-class in-cluster-friendly wrapper around the existing
watch engine. It uses in-cluster Kubernetes auth when available, supports the
same webhook/file sinks and receipt emission controls as `watch`, and can be
configured by `CUB_SCOUT_BOT_*` environment variables in Kubernetes manifests.

The new `examples/bot/` manifest provides a read-only ServiceAccount,
ClusterRole, ClusterRoleBinding, and Deployment.

### User-question table strengthened

The README's top table now includes release/event causality, status freshness,
event-consumer health, controller source revision/digest checks,
API-load-aware repeated questions, Argo app/app-of-apps onboarding boundaries,
and the five run modes.
