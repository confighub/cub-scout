# v2.8.0 Release Notes — ConfigHub Delivery Evidence and Bot Mode

> **Status:** Draft release candidate.
> **Previous release:** [`v2.7.0`](v2.7.0.md) — live delivery observability.

**Theme:** answer "what happened?", "is it fresh?", and "can I move on?" with
bounded ConfigHub evidence, and make the five run modes explicit while keeping
cub-scout read-only.

This release is additive. It does not change cub-scout's read-only boundary,
existing JSON fields, or exit-code contract.

## Highlights

### Bounded ConfigHub evidence on `gitops status` and `doctor`

`gitops status` and `doctor` now support:

```bash
./cub-scout gitops status \
  --with-confighub \
  --confighub-space prod \
  --confighub-since 24h \
  --format json

./cub-scout doctor \
  --with-confighub \
  --confighub-space prod \
  --format json
```

The shared `deliveryEvidence` JSON envelope includes:

- ConfigHub live-status writeback from `confighub.com/live-status`
- release history from `cub release list`
- unit-event history from `cub unit-event list`
- conservative in-cluster event-consumer Deployment health
- structured omissions for missing, stale, malformed, disconnected, or
  RBAC-blocked evidence

Reads are scoped to the current cub space by default, can use
`--confighub-space '*'` only when explicitly requested, and are bounded by
`--confighub-since`. The command does not consume event cursors.

`doctor --with-confighub` also emits a compact `delivery` rollup and can promote
concrete failed/stale delivery feedback, failed unit events, and unhealthy
observed event consumers into `topIssues`. Missing or inaccessible delivery
evidence remains an omission, not a failure assertion.

### Delivery and application health stay separate

Live-status parsing emits both:

- `deliveryVerdict` from sync/operation state
- `applicationHealthVerdict` from reported health state

Stale successful observations downgrade to `WATCH`. Missing evidence remains
`INCONCLUSIVE`. Delivery controllers and Kubernetes remain the status
authorities; cub-scout only reports evidence.

### Object-correlated delivery evidence on trace and explain

`trace` and `explain` now support the same bounded evidence controls:

```bash
./cub-scout trace deploy/api -n prod --with-confighub --format json
./cub-scout explain deploy/api -n prod --with-confighub --format json
```

These commands attach `deliveryEvidence` only when exact identifiers support the
join. Live-status writeback requires exact space plus Argo Application name or
ConfigHub unit slug; a non-wildcard `--confighub-space` can supply that explicit
space. Release evidence requires exact space plus target. Unit events require
exact unit ID, or unit slug plus space. Missing labels, missing space,
non-matching rows, absent event consumers, disconnected ConfigHub, and RBAC/list
failures become structured omissions.

### Delivery evidence on the activity timeline

`map activity` now supports the same bounded ConfigHub evidence controls:

```bash
./cub-scout map activity \
  --with-confighub \
  --confighub-space prod \
  --confighub-since 24h \
  --format json
```

The timeline gains `ConfigHub`-owned rows for live-status writeback, release
publication, unit events, event-consumer Deployment health, and omissions. JSON
rows include additive row-level `deliveryEvidence` details with stable
`source` values such as `confighub.liveStatus`, `confighub.release`,
`confighub.unitEvent`, `confighub.eventConsumer`, and `confighub.omission`.
Namespace filtering is conservative for ConfigHub rows: it matches only an
explicit namespace scope, not a ConfigHub space name that happens to look like a
namespace.

### Fingerprinted delivery evidence receipts

Single-resource receipts now support the same bounded delivery evidence reader:

```bash
./cub-scout receipt verify deploy/api -n prod \
  --with-confighub \
  --confighub-space prod \
  --confighub-since 24h \
  --format json \
  --out api.delivery.receipt.json
```

The receipt stores the object-correlated delivery snapshot under
`predicate.evidence.deliveryEvidence`, so ConfigHub live-status freshness,
delivery verdict, application-health verdict, recent matching releases, recent
matching unit events, event-consumer health, and structured omissions are all
covered by the receipt fingerprint. This remains supporting evidence only: the
selected receipt predicate still owns `predicate.verdict`, and delivery
controllers/application-health systems remain the authorities.

In this release, `--with-confighub` is intentionally single-resource only.
Aggregate, object-set, workload-convergence, and prerequisites receipts reject
the flag upfront rather than silently omitting delivery evidence.

### Controller-family coverage is explicit

`gitops status --format json` now includes `controllerCoverage[]`, and ASCII /
Markdown render the same facts. The coverage ledger records Flux, Argo CD,
ConfigHub, Sveltos, and Modelplane as `found`, `not_found`, `partial`, or
`unreadable`, including checked kinds, observed kinds, object counts, and
structured list omissions. This is the release's main API-load-aware honesty
upgrade: missing CRDs stay quiet, while RBAC/API failures are preserved for
operators, plugins, MCP callers, and bots.

### Observation freshness on broad reads and streams

Live inventory and event surfaces now carry explicit observation metadata so a
human, UI, plugin, or agent can tell which read produced the evidence:

- `map list --format json` entries include `observation`
- `snapshot` JSON includes top-level `observation`
- `summary list --format json` includes top-level query `observation` and
  per-record `entries[].observation` for stored summary evidence
- `watch` / `bot` events include top-level `observation`
- `receipt list --format json` includes `freshness.status` derived from saved
  receipt TTL stamps

The shared object includes a source (`kubernetes-api` for live reads,
`summary-store` for connected summary storage), a producing `mode` (`map-list`,
`snapshot`, `summary-list`, or `watch-poll`), `observedAt`, `freshness:
point-in-time`, and optional cluster/namespace/kind scope. This is a freshness
boundary only; it is not a TTL or a claim that the object remained unchanged
after the observation. For summary records, `observedAt` is the persisted record
timestamp, not proof of a fresh Kubernetes API read.

Saved receipts use their existing immutable `predicate.freshness` stamp instead
of `observation`: `receipt list` reports `fresh`, `stale`, `not-declared`, or
`invalid` at list time without touching the Kubernetes API or rewriting the
receipt artifact.

### Modelplane-on-Crossplane substrate evidence

Modelplane evidence now preserves Modelplane as the higher-level owner while
surfacing Crossplane composition substrate evidence when present:
`crossplane.io/composite`, `crossplane.io/claim-*`,
`crossplane.io/composition-resource-name`, and verified Crossplane field-manager
strings.

The structured field appears in:

- `map list --format json` as `ownerEvidence`
- `watch` / `bot` events as `owner.evidence`
- `receipt verify --format json` and watch/bot inline receipts as
  `predicate.evidence.platformSubstrate`

Trace human/Markdown output renders the same facts as a
`Modelplane-on-Crossplane evidence: ...` message. This is a conservative
trace/explorer/watch/bot/receipt parity step; deeper object-level source and
generation joins across every Crossplane layer remain follow-up work.

### MCP GitOps and connected parity

Standalone MCP mode now includes `gitops_status`, a read-only wrapper for
`gitops status --format json`, so agents can ask delivery-health and
controller-coverage questions without freehand shelling.

Connected MCP mode adds read-only tools for the same evidence:

- `confighub_live_status`
- `confighub_releases`
- `confighub_unit_events`

`compare_source_truth` now derives its strategy enum from the same registry as
the CLI, closing the previous MCP/CLI strategy drift.

### Five run modes and bot mode

The README now opens with the five supported ways to run cub-scout:

- standalone client
- ConfigHub plugin
- MCP server
- watch stream
- in-cluster bot

`cub-scout bot` is a first-class in-cluster-friendly wrapper around the existing
watch engine. It uses in-cluster Kubernetes auth when available, supports the
same webhook/file sinks and receipt emission controls as `watch`, and can be
configured by `CUB_SCOUT_BOT_*` environment variables in Kubernetes manifests.

The new `examples/bot/` manifest provides a read-only ServiceAccount,
ClusterRole, ClusterRoleBinding, and Deployment.

### User-question table strengthened

The README's top table now includes release/event causality, status freshness,
event-consumer health, ConfigHub activity timeline evidence, controller source revision/digest checks,
API-load-aware repeated questions, observation freshness metadata,
receipt-store freshness summaries,
Argo app/app-of-apps onboarding boundaries, and the five run modes.
