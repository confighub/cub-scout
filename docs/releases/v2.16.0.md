# v2.16.0 — Works with ConfigHub 0.11; answers in one shape

**Not yet published.** This page describes what `main` holds for v2.16.0. The
release before it is [v2.15.1](v2.15.1.md).

**If you use cub-scout with hosted ConfigHub, upgrade.** v2.15.1 refuses a
ConfigHub 0.11 server, and hosted ConfigHub is on 0.11.

Read [Behaviour changes to expect](#behaviour-changes-to-expect) before
upgrading if you match on `trace` warning text, or consume `trace` or
`compare source-truth` JSON. Both get larger.

## Fixed

- **Works with ConfigHub 0.11.** Hosted ConfigHub reports v0.11.3.
  cub-scout v2.15.1 is built with ConfigHub SDK core v0.10.11, and it refuses
  a server a minor version ahead. So every connected command fails against
  hosted ConfigHub by default. v2.16.0 is built with SDK core v0.11.4
  ([#925](https://github.com/confighub/cub-scout/pull/925)); no source change
  was needed. Standalone use is not affected. On v2.15.1 the workaround is
  `CUB_SCOUT_CONFIGHUB_READER=cub` with an up-to-date `cub`.
- **`trace` answers in JSON for a resource with no owner marker**
  ([#915](https://github.com/confighub/cub-scout/pull/915)). Before, it printed
  an error line and no JSON. `trace --format json` now returns an answer with
  `reason: "no-owner-marker-recognised"`. The warning reads "no GitOps owner
  marker was recognised on this resource" in place of "resource not managed
  by ...". The exit code is still 1.
- **`trace --artifacts` says "not applicable"** for a source with no object
  of its own, such as an Argo CD Application's Git or OCI source. It printed
  nothing before ([#911](https://github.com/confighub/cub-scout/pull/911)).
- **Docs say "no owner marker recognised", not "not managed"**, in the
  glossary, the FAQ and the main how-tos
  ([#923](https://github.com/confighub/cub-scout/pull/923)).
- A test race in the bounded-exec tests is fixed
  ([#913](https://github.com/confighub/cub-scout/pull/913)). This changes tests
  only.

## New

- **An `answer` block on `trace`**
  ([#920](https://github.com/confighub/cub-scout/pull/920)). It carries
  `state`, `reason`, `summary`, `observedAt`, `cluster`, `basis`, `unknowns`,
  `next` and `cost`. `state` is `traced`, `chain-not-ready`, `no-owner-marker`
  or `not-observable`. `traced` means every delivery controller in the chain
  reports ready. It does not mean the workload is healthy. `cost` counts the
  requests and bytes of the trace's own Kubernetes clients.
- **A lean `answer` on `compare source-truth`**
  ([#922](https://github.com/confighub/cub-scout/pull/922)).
  It carries `state` (`agreed`, `not-agreed`, `incomplete`, `not-observable`),
  `reason`, `observedAt`, `unknowns` and `next`. When agreed, the reason names
  what was compared. Every `agreed` answer says what it did not compare: under
  a ConfigHub OCI strategy the digest, under the Git and plain OCI strategies
  ConfigHub's record. The full block would have more than doubled this small
  answer, so this command carries the lean form.
- **A tool profile for `mcp serve`**
  ([#918](https://github.com/confighub/cub-scout/pull/918), design in
  [#917](https://github.com/confighub/cub-scout/pull/917)).
  `mcp serve --tools all|core|<names>`, or the `CUB_SCOUT_MCP_TOOLS`
  variable. The default is `all`, so nothing changes unless you ask for a
  profile. `core` lists four tools, plus two more with a ConfigHub session,
  and a new tool, `cub_scout_more`. That tool lists, describes and runs the
  tools a profile leaves out. An exact list is an allow-list: an unlisted tool
  cannot be called. The tool catalog is 15,120 bytes for all 8 standalone tools
  and 9,292 for `core`. With ConfigHub it is 31,126 and 12,239.
- **Measured answer sizes**
  ([#916](https://github.com/confighub/cub-scout/pull/916)). The `live-status`
  lane records, on Flux and Argo CD, the bytes of cub-scout's JSON against
  `kubectl get ... -o json` for four questions. The method and caveats are in
  [answer-sizes.md](../reference/answer-sizes.md).

| Question | Flux: cub-scout / raw | Argo CD: cub-scout / raw |
|---|---|---|
| Which source and revision delivered this workload? (`trace`) | 4,564 / 12,679 (36%) | 6,383 / 15,690 (41%) |
| Do ConfigHub, the controller and the workload agree? (`compare source-truth`) | 1,239 / 12,679 (10%) | 1,232 / 15,690 (8%) |
| What do the delivery controllers report? (`gitops status`) | 3,787 / 16,549 (23%) | 2,911 / 17,671 (16%) |
| Who owns this resource, with no owner marker? (`trace`) | 1,576 / 8,432 (19%) | 1,576 / 8,432 (19%) |

From `live-status` run 43836709515, with the `answer` blocks in place. Without
them `trace` was 2,734 bytes on the Flux chain and `compare source-truth` 909.
These are bytes. They are not a measure of correctness or of what an agent
spends. An agent also pays for the tool catalog once a session, so one
question a session does not repay it.

## Behaviour changes to expect

- **The `trace` warning text changed, and there is a new `reason`.** For a
  resource with no recognised owner marker, match on `reason` ==
  `no-owner-marker-recognised`. Do not match on the text. A consumer that
  looked for "resource not managed by" will stop matching.
- **`trace` JSON is larger.** A Flux chain went from 2,734 to 4,564 bytes, an
  Argo CD chain from 4,767 to 6,383, a resource with no owner marker from 847
  to 1,576. The `answer` block repeats some of what `chain` holds; that
  duplication goes in 3.0.
- **`compare source-truth` JSON is larger.** On the real clusters it went from
  about 905 to about 1,235 bytes.
- **`initialize` from `mcp serve` reports `serverInfo.toolProfile`.**
- **Deprecation notice.** In 3.0 the verdict words `status` (`PASS`, `WATCH`,
  `ASK`, `BLOCK`) and `source_truth` (`AGREED` and the rest) leave the JSON and
  MCP output of `compare source-truth`. They stay in its ASCII and Markdown
  output. Decide on `answer.state` and `answer.reason`.

## Limits

- The `answer` block is on `trace` and `compare source-truth` only.
  `gitops status`, `explain` and `doctor` do not carry it.
- `chain[].ready` in `trace` is unchanged. It can be true for a link that
  nothing read.
- `compare source-truth` still compares no digest under the ConfigHub OCI
  strategies.
- The `answer.cost` figures do not count requests made by a `flux` subprocess.
- The default MCP tool profile is unchanged. It is still `all`.

## What was and was not verified

- **Against a real ConfigHub v0.11.4, in CI.** The Connected lane (run
  43835428929) installs a disposable server and compares cub-scout's reads
  with `cub`'s; it passed. The `live-status` lane (run 43836652534) attached
  clusters with `cub cluster up` for Flux, Argo CD and Sveltos and passed.
  Hosted ConfigHub itself was not used.
- **On real clusters, in CI.** The `live-status` lane requires: `trace` to
  answer `traced` for a delivered workload and `no-owner-marker` for
  `coredns`, with a time, whose word each link rests on and a measured cost;
  `compare source-truth` to answer `agreed` by `object-revision-is-head` with
  one `not-compared` unknown and the time of the run. Run 43836709515 passed
  on Flux and Argo CD.
- **Independent review.** #918, #920 and #922 were each read by a reviewer
  that did not write them, after CI was green. Each review found faults that
  were fixed before merge: an allow-list that could be bypassed, readiness
  reported for chain links nothing had read, and an `agreed` answer that did
  not say what it had not compared.
- **The `live-status` lane is pinned to `ubuntu-24.04`.** On 2026-11-16 it
  failed three times on `ubuntu-26.04`, which `ubuntu-latest` now resolves to:
  after `cub cluster up` no controller became available. It passes on 24.04.
  Why 26.04 fails is not known. cub-scout itself is not involved; the lane's
  cluster set-up is.
- **Not seen on a real cluster:** a chain that is not ready; a
  `not-agreed` or `incomplete` source-truth answer; `--tools core` driven by
  an agent.
- **Not measured:** whether the `answer` block, the shorter catalog or the
  `core` tool profile changes what an agent spends or which tool it picks. No
  paid eval run was made for this release; the eval cases for #915, #918,
  #920 and #922 are waived for that reason.
- **What ConfigHub 0.11 changed** is not known to this project: the SDK
  releases carry no notes. Nothing cub-scout reads broke.
