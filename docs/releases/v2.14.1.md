# v2.14.1 — An empty filter is refused, and the plugin's skills match v2.14

**Unreleased.** Published baseline is [v2.14.0](v2.14.0.md). This page is the
notes for the next release, cut from `main`.

A correction release. One fix to command behaviour, the plugin's skills
brought up to date with v2.14.0, and corrections to the docs. The ConfigHub
SDK is unchanged at v0.8.12, and nothing here changes how ConfigHub is read.

## Fixed

- **An empty filter is refused, not treated as no filter**
  ([#877](https://github.com/confighub/cub-scout/pull/877)). A filter given an
  empty value used to run unfiltered, so the whole cluster came back as the
  answer to a narrower question. The usual way to hit it is a script whose
  variable is unset:

```bash
cub scout gitops settings --project "$PROJECT" --format json   # as a cub plugin
./cub-scout gitops settings --project "$PROJECT" --format json # standalone
```

  These now exit 1 with a message, before anything is read:

  | Where | Refused |
  |---|---|
  | `gitops settings` | `--project` or `--setting` given only an empty value |
  | `gitops tree` | `--kind`, `--sync` or `--health` given only an empty or blank value |
  | MCP `gitops_settings` | an empty `setting` or `project` array |

  Leaving a filter out still means no filter. In `gitops tree`, a blank among
  real values (`--kind "Deployment,"`) is still dropped and the real values
  still filter. The MCP tool's input schema is unchanged; the refusal is made
  by the tool.

## The plugin's skills

The skills installed with the plugin described v2.13
([#875](https://github.com/confighub/cub-scout/pull/875)). They now say:

- connected mode is `confighub_reads: true` in `status --json`, a check made
  through the ConfigHub SDK with no `cub` binary, where they said
  "`cub auth status` reports OK";
- there are 21 MCP tools, 8 standalone and 13 connected, where they said 17 or
  19, and `gitops_settings`, `release_check`, `confighub_attestations` and
  `confighub_changeorder_get` are listed wherever they were missing;
- which connected tools read through the SDK and which still run `cub`.

**Whether the corrected text changes what an agent does was not measured.** No
agent eval was run. The recorded runtime diagnostic, which pins the skills,
was re-pinned and re-run on the new text; it uses a fake provider and shows
only that the skills still load.

## Docs corrected

- **The v2.14.0 notes and the SDK reference listed `release check` among the
  reads that still need `cub`.** It reads the cluster and an OCI registry and
  never needed `cub`. Both pages are corrected.
- `status --json`: when `auth_valid` is absent and when it is `false`
  ([#874](https://github.com/confighub/cub-scout/pull/874),
  [#878](https://github.com/confighub/cub-scout/pull/878)).
- The roadmap pages carry the renumbering: the P4 gates are v2.15, P5 is
  v2.16, P6 is 3.0.
- Four dead links in the JSON contracts page.

## Limits

- Nothing in [v2.14.0's limits](v2.14.0.md#limits) has moved: one server
  version, no hosted server, no ordinary user's session, no token renewal.
- The filter fix covers the repeatable filters of `gitops settings` and
  `gitops tree`. The CLI's other repeatable flags (`--label`, `--resource`,
  the receipt inputs) are not read filters of this kind. Single-value flags
  such as `--namespace` were not examined.

## What was and was not verified

Verified before publication:

- required CI on `main` at the tagged commit: Unit Tests, Integration Tests,
  GitOps E2E and Proof Artifact; and a clean local build, `go vet ./...` and
  `go test ./...` on that commit;
- each of the three refusals by a unit test that fails without its fix, and
  the built binary refusing `gitops settings --project=`, `--setting=` and
  `gitops tree --health ""` with exit 1 and no Kubernetes client built;
- the skills' statements about tools and routes against the code, by an
  independent review whose nine findings are fixed.

Not verified, and not claimed:

- the filter refusals against a live cluster or a live MCP client: they are
  made before any read;
- any agent eval for the skills or the fix;
- anything on a hosted ConfigHub, or with a credential that is not an
  administrator's;
- Full Verification and most of Demo Tests, which still stop at the private
  scanner credential (#774); Windows binaries are not executed.
