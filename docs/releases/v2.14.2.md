# v2.14.2 — Live status is read from each Release

**Published 2026-10-26.** [Release and assets](https://github.com/confighub/cub-scout/releases/tag/v2.14.2)
at source `f5ca8e513ed27066f6577273e3dda6fe8e9565f0`. The
[tagged tests and packaging run](https://github.com/confighub/cub-scout/actions/runs/40410010499)
passed. What was checked on the published artifacts is under
[Publication checks](#publication-checks). The release before it is
[v2.14.1](v2.14.1.md).

A correction release, for one change in ConfigHub.

## Fixed

- **Live status is read where ConfigHub now records it**
  ([#883](https://github.com/confighub/cub-scout/pull/883), refs
  [#882](https://github.com/confighub/cub-scout/issues/882)). Since a ConfigHub
  server change of 2026-10-03, the tool deploying a Release (argobot, for
  Argo CD, Flux or Sveltos) records what it sees on the Release itself, and
  nothing writes the `confighub.com/live-status` Space annotation any more.
  `gitops status --with-confighub` and the MCP `confighub_live_status` tool
  read only that annotation, so on a current server they reported no live
  status for every space. They were not wrong, but the evidence was somewhere
  they did not look.

```bash
cub scout gitops status --with-confighub --confighub-space prod --format json   # as a cub plugin
./cub-scout gitops status --with-confighub --confighub-space prod --format json # standalone
```

  Both now read the Releases created in the window (`--confighub-since`,
  default 24h; the MCP tool takes an optional `since`) and report, for each
  Space and Target, the newest Release that has a status. The annotation is
  still read, for older servers. Each row says where it came from
  (`recordedOn: release` or `space-annotation`), and a Release row names its
  Release and Target. The freshness rules are unchanged: only a fresh status
  can give PASS or BLOCK.

## Behaviour changes to expect

- **New fields** on `liveStatuses[]`: `recordedOn`, `release`, `releaseId`,
  `target`, `dataSource`, `reporterSync`, `reporterHealth`,
  `reporterOperation`. Existing fields keep their meaning. See the
  [JSON contracts](../reference/json-contracts.md).
- **The MCP `confighub_live_status` answer changes shape.** Its text is now
  `{spaces, releases, releasesSince}` as read (or `releasesError`), where it
  was the space list. `structuredContent.liveStatuses[]` and `omissions[]` are
  where an agent should read, as before.
- **One more ConfigHub read** for that tool: the Releases of the space in the
  window, through the ConfigHub SDK for one named space.
- **A Release's status from before the window is not read.** Widen
  `--confighub-since` (or `since`) to include it; the omission for a space with
  no status says so.

## Also in this release

- The Flux example in `examples/flux-boutique/` now pins podinfo to its
  `6.16.0` tag. It followed `master`, which on 2026-10-26 named an image
  before it was published, so the example could not start.

## Limits

- `map activity` joins live status to an Argo CD Application by name; a
  Release's status has no Application name, so it is not joined there.
- The plugin's `scout-mcp` skill still describes this tool as reading the
  space list only; the tool catalog page is updated.
- Nothing in [v2.14.0's limits](v2.14.0.md#limits) has moved.

## What was and was not verified

Verified before publication:

- required CI on `main` at the tagged commit, and a clean local build,
  `go vet ./...` and `go test ./...` on that commit;
- on a real ConfigHub v0.8.12 in the Connected E2E lane: a `LiveStatus`
  written on a Release with the merge patch argobot sends, then reported by
  the built binary's MCP tool from the Release; the server's answers are kept
  as test fixtures;
- unit tests on recorded server output, and three mutations of the new logic,
  each caught.

Not verified, and not claimed:

- with argobot itself, or with a status a deploying tool wrote: the test wrote
  the values;
- anything on a hosted ConfigHub;
- any agent eval for the change;
- Full Verification and most of Demo Tests, which still stop at the private
  scanner credential (#774); Windows binaries are not executed.

## Publication checks

Made on 2026-10-26 against the published artifacts:

- the six archives and `checksums.txt` are on the release, and every archive
  matches its checksum;
- the macOS arm64 binary, the macOS amd64 binary (under Rosetta) and the Linux
  arm64 and amd64 binaries (in read-only containers with no capabilities)
  each report `2.14.2` and `ConfigHub SDK v0.8.12`;
- the published macOS arm64 binary's `mcp serve`, with a private, empty cub
  configuration, lists the 8 standalone tools;
- `cub plugin install confighub/cub-scout@v2.14.2` installs with a private
  home and cub configuration, and `cub scout version` reports `2.14.2`;
- the Go module proxy serves `v2.14.2` at the tagged commit as `@latest`;
- the Homebrew formula names the v2.14.2 source archive with its SHA-256, and
  the cask's macOS arm64 checksum is the published archive's.

Not checked: `brew install`; running the Windows binaries; an anonymous pull
of the container image, which the registry denies (#520); any ConfigHub
request with the published binary. The Release live-status read was checked
on a real server in CI on the same source, not with the published binary.
