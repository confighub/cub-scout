# cub-scout v0.19.1 — UX Hardening & New User Onboarding

**Status:** Planned
**Audience:** Maintainers, contributors, and new users
**Scope:** UX correctness, demo reliability, onboarding clarity
**Non-goals:** No new semantics, schemas, inference, or connected-mode expansion

---

## Why v0.19.1 Exists

v0.19 successfully delivered **TUI polish and behavioral locking**.
This release focuses on a different goal:

> **Make the first hour with cub-scout honest, predictable, and confidence-building.**

The issues addressed here are not about missing capability — they are about **trust**, **clarity**, and **first impressions**.

---

## Guiding Principles

v0.19.1 follows these rules:

- Never show green for broken states
- Never show red for healthy systems
- Demos must fail clearly or succeed meaningfully — never silently degrade
- Errors must explain *why*, not just *what*
- Guidance should help, not intimidate (no "rules" for new users)

---

# Part I — v0.19.1 Execution Plan (UX Hardening)

## 1. Trace Command Misclassifies Healthy Flux Resources (#107)

**Severity:** High
**Component:** `trace`

### Problem

Flux resources with `Ready=True` are rendered as errors, causing:
- Red X for healthy deployments
- Misleading "Chain broken" messages
- Loss of user trust

### Fix

- Parse Flux conditions semantically:
  - `Ready=True` → checkmark (info)
  - `Ready=False` → X (error)
- Only mark the chain broken when a true failure exists
- Preserve explanatory messages, but classify them correctly

### Acceptance Criteria

- `trace` output agrees with `gitops status`
- Healthy resources never display red X

---

## 2. Status Shows "Connected" With Expired ConfigHub Token (#108)

**Severity:** High
**Component:** `status`

### Problem

`status` reports "Connected" even when the auth token is expired, leading to confusing failures later.

### Fix

- Perform lightweight auth validation during `status`
- Introduce explicit states:
  - `Connected`
  - `Connected (auth expired)`
  - `Disconnected`
- Include remediation hint: `Run: cub auth login`

### Acceptance Criteria

- Users are warned *before* commands fail due to auth
- No false green "Connected" indicators

---

## 3. CCVE Demo Namespace Wiring Broken (#109)

**Severity:** Medium
**Component:** `demo ccve`

### Problem

Demo deploys resources into one namespace and scans another, then reports "No issues found".

### Fix

- Correct namespace references
- Add CI assertion that the CCVE is detected

### Acceptance Criteria

- `demo ccve` always demonstrates the vulnerability
- Demo output is deterministic and meaningful

---

## 4. Demo System Lacks Prerequisite Awareness (#106)

**Severity:** High
**Component:** `demo`

### Problem

Demos silently degrade when GitOps CRDs (Flux/Argo) are missing, producing misleading results.

### Fix

- Add demo preflight checks:
  - Flux CRDs
  - Argo CRDs (when relevant)
- On failure:
  - Stop execution
  - Explain what's missing
  - Provide next steps: `flux install`, `--mock` mode, docs reference

### Acceptance Criteria

- No demo runs in a degraded state without explanation
- Users always know *why* output looks the way it does

---

## 5. Import Error Messages Lose Root Cause (#112)

**Severity:** Medium
**Component:** `import`

### Problem

Errors like `exit status 1` obscure actionable causes (e.g. expired token).

### Fix

- Propagate underlying error messages
- Surface clear cause and remediation

### Acceptance Criteria

- Import failures explain what failed and how to fix it

---

## 6. Demo Help Text Flag Mismatch (#110)

**Severity:** Low
**Component:** CLI help

### Fix

- Align help text with actual syntax
- Or add `--list` as an alias

---

## 7. Invalid --owner Flag Returns Silent Empty Results (#111)

**Severity:** Low
**Component:** CLI flags

### Fix

- Validate `--owner` flag values
- Return error with valid options list

---

## 8. Example Scripts Block Automation

**Severity:** Low
**Component:** examples

### Fix

- Add `-y / --yes` flag or `CUB_SCOUT_ASSUME_YES=1`
- Scripts must be non-interactive by default

# Part II — New User Onboarding Checklist (Advisory)

> **Purpose:**
> Help new users understand their environment so cub-scout's output makes sense.
> This is guidance, **not a set of rules**.

This checklist should appear in:
- Getting Started docs
- Optionally: `cub-scout status --verbose`

---

## Before You Start (Helpful Checks)

You can use cub-scout without all of these —
but results will be **richer and more informative** when they apply.

---

### GitOps Controllers (Optional, Recommended)

cub-scout understands GitOps ownership and lineage when controllers are present.

- Flux installed: ownership, trace, and attribution work best
- ArgoCD installed: hook and ordering insights available

If not installed:
- cub-scout still works
- resources may appear as **Native**

---

### Cluster Access

- Read-only access is sufficient
- cub-scout never mutates cluster state

If access is limited:
- some relationships may be unavailable
- cub-scout will indicate degraded views

---

### Connected Mode (Optional)

If authenticated with ConfigHub:
- ensure your token is valid
- `cub-scout status` will warn if it's expired

Connected mode enhances:
- history
- fleet views
- comparisons

Standalone mode remains fully functional.

---

### Demos

Some demos expect specific capabilities:

- GitOps demos: Flux or Argo CRDs
- CCVE demos: specific namespaces

If prerequisites are missing:
- cub-scout will explain what's needed
- mock demos are available for exploration

---

### Interpreting Output

- Checkmark (green): healthy
- Warning (yellow): partial or degraded
- X (red): broken or missing

If something looks wrong:
- try `--verbose`
- run `gitops status`
- check `status` for environment hints

---

## Philosophy Reminder

cub-scout does not:
- apply changes
- enforce policy
- guess intent

It explains **what exists**, **why**, and **what context may be missing**.
