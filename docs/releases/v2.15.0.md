# v2.15.0 — Works with ConfigHub 0.10; bridge workers are gone

**Published 2026-11-10.** [Release and assets](https://github.com/confighub/cub-scout/releases/tag/v2.15.0)
at source `f723eced54d9420e418e1d3fe42fa99192cd3628`. The
[tagged tests and packaging run](https://github.com/confighub/cub-scout/actions/runs/42891637683)
passed. What was checked on the published artifacts is under
[Publication checks](#publication-checks). The release before it is
[v2.14.2](v2.14.2.md).

ConfigHub API 0.10 (2026-10-31) removed bridge workers. Hosted ConfigHub is on
v0.10.11. cub-scout v2.14.2 is built with ConfigHub SDK v0.8.12 and **refuses a
0.10 server by default**, so every connected command fails there until you
upgrade. Standalone use, with no ConfigHub, is not affected.

## Fixed

- **Connected commands work against ConfigHub 0.10**
  ([#900](https://github.com/confighub/cub-scout/pull/900), refs
  [#897](https://github.com/confighub/cub-scout/issues/897)). cub-scout is
  built with ConfigHub SDK core v0.10.11. On a real ConfigHub v0.10.11 in CI,
  its reads matched `cub` v0.10.11 byte for byte on the 22 reads recorded by
  both routes.
- **The live-status cluster check works on a cluster attached with
  `cub cluster up`** ([#901](https://github.com/confighub/cub-scout/pull/901),
  refs [#887](https://github.com/confighub/cub-scout/issues/887)). Such a
  cluster reaches a local server's registry at an address the server does not
  advertise, so no controller was recognised and every check came back
  `not-observable`. See the next section.

## New

- **`gitops status --with-confighub` says whether this cluster agrees with the
  live status the deploying tool recorded**
  ([#896](https://github.com/confighub/cub-scout/pull/896),
  [#901](https://github.com/confighub/cub-scout/pull/901)). ConfigHub gates on
  the `LiveStatus` argobot records on a Release. For each such status,
  `clusterCheck` compares it with what the Argo CD Application or Flux
  Kustomization in the cluster you are looking at reports about that Release's
  manifest digest: `agrees`, `disagrees` or `not-observable`, with the reason
  and the controllers compared.

```bash
cub scout gitops status --with-confighub --confighub-space prod --format json   # as a cub plugin
./cub-scout gitops status --with-confighub --confighub-space prod --format json # standalone
```

  It compares two reports and is not a verdict: health is not compared, a
  controller's report is not proof that workloads converged, and the cluster
  read may not be the Release's Target. Every answer carries that limitation.
  It is `not-observable`, never agreement, when the status is stale, a newer
  Release has no status yet, a controller has not settled, or no controller
  can be tied to the Release's space. `matchedBy` says how the controller was
  found: by the ConfigHub registry, or, where the registry address is not the
  advertised one, by being the object the status itself names as its data
  source.
- **`explain` names the first link of a delivery chain that is not ready**
  ([#895](https://github.com/confighub/cub-scout/pull/895), refs
  [#827](https://github.com/confighub/cub-scout/issues/827)), as a
  machine-readable `summary.deliveryBlockedAt` with kind, name, namespace,
  status and reason.

## Removed, because ConfigHub removed it

ConfigHub 0.10 has no bridge workers, no `cub worker`, no
`cub unit set-target` and no provider on a target. A Space releases to a
Target, and a GitOps controller on a cluster attached with
`cub cluster attach` pulls the Release.

- **`import --connect` refuses**, says why, and points to
  `cub cluster attach`. It used to start a worker and point each new unit at
  the worker's target. `--no-connect` is accepted and ignored. `import` on its
  own no longer connects anything; it ends by saying the units are not yet
  delivered.
- **Worker status is gone** from `status` (the `worker` field leaves
  `status --json`), from `map --hub` (the Workers group, the counts, the
  header and the disconnected warning) and from the cluster TUI's header.
- **The import wizards no longer create a worker, set a target or run an
  end-to-end test.** `import --wizard` loses the `w` and `t` keys and its test
  step; the import flow in `map --hub` loses its worker, target and
  "test pipeline" steps. Both end by naming `cub cluster attach`.
- **The create wizard in `map --hub`** makes a target from a name alone, and
  no longer offers a target when creating a unit.
- **`./demo.sh --live`** in `examples/argo-import-confighub-demo` and
  `examples/flux-import-confighub-demo` refuses with an explanation. The
  observe-only runs are unchanged.

## Behaviour changes to expect

- **Go 1.26 to build from source** (`go install`), which SDK core v0.10.11
  requires. The published binaries need nothing.
- **A ConfigHub server older than 0.10 was not tried with this build.** If you
  run one, stay on v2.14.2 until you have checked.
- **New fields:** `liveStatuses[].clusterCheck` (with `matchedBy`) and
  `summary.deliveryBlockedAt`. See the
  [JSON contracts](../reference/json-contracts.md).
- **A removed field:** `worker` in `status --json`.

## Limits

- The cluster check reads Argo CD Applications and Flux Kustomizations. It
  does not read Sveltos, and it does not compare health.
- cub-scout does not read ConfigHub channels, which took over from workers as
  the way a bot connects. Nothing replaces the worker status
  ([#898](https://github.com/confighub/cub-scout/issues/898), not planned).
- Demo helper scripts under `examples/scripts/` that drive `cub worker` fail
  against a current `cub`
  ([#899](https://github.com/confighub/cub-scout/issues/899)).
- Nothing in [v2.14.0's limits](v2.14.0.md#limits) has moved.

## What was and was not verified

Verified before publication:

- required CI on `main` at the tagged commit, and a clean local build,
  `go vet ./...` and `go test ./...` on that commit;
- on a real ConfigHub v0.10.11 with `cub` v0.10.11, in the Connected E2E lane
  ([run 42876296858](https://github.com/confighub/cub-scout/actions/runs/42876296858)):
  the import round trip and the six reader parity tests;
- on real clusters attached with `cub cluster up`, with argobot itself writing
  the status
  ([run 42879836132](https://github.com/confighub/cub-scout/actions/runs/42879836132)):
  the cluster check reports `agrees` for both Releases under Flux and under
  Argo CD. The server's and clusters' answers are kept as test fixtures;
- the Windows binaries build and start on amd64 and arm64
  ([run 42868061168](https://github.com/confighub/cub-scout/actions/runs/42868061168),
  before the last TUI-only commits);
- an independent read-only review of the TUI and import removal, which found
  one defect, fixed before merge.

Not verified, and not claimed:

- anything on a hosted ConfigHub, or on a server older than 0.10;
- a Release that is out of sync, or a disagreement, on a real cluster: those
  are covered by unit tests only;
- Sveltos; a deployment space created with `cub variant create --target`;
- any agent eval for these changes (waived);
- the removed TUI flows by hand in a terminal: they are covered by unit and
  snapshot tests;
- Full Verification and most of Demo Tests, which still stop at the private
  scanner credential (#774).

## Publication checks

Made on 2026-11-10 against the published artifacts:

- required CI passed on `main` at the tagged commit
  ([run 42888868388](https://github.com/confighub/cub-scout/actions/runs/42888868388))
  before the tag was pushed;
- the six archives and `checksums.txt` are on the release, and every archive
  matches its checksum;
- the macOS arm64 binary, the macOS amd64 binary (under Rosetta) and the Linux
  arm64 and amd64 binaries (in read-only containers with no capabilities and
  no network) each report `2.15.0` and `ConfigHub SDK v0.10.11`;
- the published macOS arm64 binary's `mcp serve`, with a private, empty cub
  configuration, lists the 8 standalone tools;
- `cub plugin install confighub/cub-scout@v2.15.0` installs with a private
  home and cub configuration, and `cub scout version` reports `2.15.0`;
- the Go module proxy serves `v2.15.0` at the tagged commit as `@latest`;
- the Homebrew formula names the v2.15.0 source archive with its SHA-256,
  which matches that archive, and the cask's macOS arm64 checksum is the
  published archive's.

Not checked: `brew install`; running the Windows binaries; an anonymous pull
of the container image, which the registry denies (#520); any ConfigHub
request with the published binary. The reads against ConfigHub v0.10.11 and
the live-status proof were made in CI on the same source, not with the
published binary.
