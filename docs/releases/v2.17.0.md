# v2.17.0 — Ownership checked against real installs

**Not yet published.** This page describes what `main` holds for v2.17.0. The
release before it is [v2.16.0](v2.16.0.md).

Helm, kro, Crossplane and Terraform were each installed for real in CI, beside
the Flux and Argo CD already there, and what each tool writes on the objects it
creates was recorded. That found faults in the handling of three of them, and a
Terraform detector that matched keys no tool writes. Modelplane has not yet
been installed this way.

Read [Behaviour changes to expect](#behaviour-changes-to-expect) before
upgrading if you count objects owned by Terraform, consume `trace` JSON for
Helm-installed objects, or read kro owner names.

## Fixed

- **kro: the owner's name is the instance's**
  ([#936](https://github.com/confighub/cub-scout/pull/936)).
  - kro v0.10.0 wrote nine `kro.run/` labels on the object it created in CI, and
    sets no owner reference. Most of those labels name nothing:
    `kro.run/owned` is `true`, `kro.run/kro-version` is a version and
    `kro.run/instance-id` is a UID.
  - The detector took the owner's name from whichever `kro.run/` label Go's
    map order gave first. So on a real kro object the reported owner could be
    `true`, a version, a UID or the instance, and changed from run to run.
  - The name now comes from `kro.run/instance-name`. Any other `kro.run/`
    label still means kro owns the object, with the name unknown, and the
    answer is the same every time.
  - The composition tree resolves the instance and its
    `ResourceGraphDefinition` from kro's labels.
- **Helm: `trace` answers for objects named only by Helm's annotations**
  ([#929](https://github.com/confighub/cub-scout/pull/929),
  [#933](https://github.com/confighub/cub-scout/pull/933)).
  - For an object whose chart sets no `app.kubernetes.io/instance` label,
    `trace --format json` printed nothing. Most charts set none. `trace` now
    reads the release named by Helm's own `meta.helm.sh/release-name` and
    `release-namespace` annotations.
  - A release named by those annotations, or by the instance label, is claimed
    only if its stored manifest (or a hook's) lists the object. A copied
    object, which keeps the annotations, is credited to no release. Before,
    the instance label was taken on trust.
  - Helm's annotations take precedence over the label: they are Helm's
    record, while the label is the chart's, and Argo CD writes the same label.
- **`trace` says "no owner marker" only when none was recognised**
  ([#929](https://github.com/confighub/cub-scout/pull/929)). An object
  carrying Helm's marker, whose named release does not list it, was answered
  "No GitOps owner marker was recognised". It is now `not-observable`, and the
  answer names the marker it carries.
- **`tree composition`: a Crossplane composite is its own root**
  ([#940](https://github.com/confighub/cub-scout/pull/940)). Crossplane labels
  a composite `crossplane.io/composite` with its own name. The tree showed the
  composite a second time, under a made-up `CompositeResource` parent. A
  composed object that shared the composite's name was shown as a root.
- **kubectl warnings are no longer parsed as data**
  ([#938](https://github.com/confighub/cub-scout/pull/938)). kubectl 1.35
  prints deprecation warnings on stderr. Read with stdout and stderr combined, the warnings made
  `tree composition` skip Endpoints and Crossplane Usages as undecodable. The
  manifest that `import` uploads to ConfigHub could have contained a warning
  too. Both now read stdout alone.

## Changed

- **Terraform is no longer detected from two keys no Terraform tool writes**
  ([#942](https://github.com/confighub/cub-scout/pull/942)).
  - The detector read `app.terraform.io/run-id` and `app.terraform.io/managed`.
    A code search finds them nowhere but in cub-scout and the code it was
    copied from.
  - Terraform 1.17.2 with the `hashicorp/kubernetes` provider 3.5.0 wrote no
    label or annotation at all. It left only a field manager: `HashiCorp` for
    typed resources, `Terraform` for `kubernetes_manifest`.
  - The detector is removed. When the field manager `explain` reports is one
    of these, `explain` says which Terraform resource type writes with it, in a
    new `mutationManagerTool` field and in its text. That is evidence of who
    wrote the fields, not an ownership claim.
- **A Helm release's recorded status is read**
  ([#935](https://github.com/confighub/cub-scout/pull/935)).
  - A Helm chain was always answered `readiness-not-read`. If Helm records the
    release as `deployed`, the answer is now `traced`; any other status gives
    `chain-not-ready`.
  - The claim rests on `deployer-report`, not `controller-report`. `unknowns`
    says Helm writes this status when it installs or upgrades the release and
    does not watch the objects afterwards.
- **Helm chain links have roles**
  ([#933](https://github.com/confighub/cub-scout/pull/933)). `Release` is a
  `deployer` and `HelmChart` is `intermediate`. Before, both were `workload`.
  This applies to `HelmChart` links from Flux and Argo CD too.

## Behaviour changes to expect

- **Nothing reads as owned by Terraform.** An object that carried
  `app.terraform.io/run-id` or `app.terraform.io/managed` read as Terraform's;
  it now reads as having no owner marker. Terraform 1.17.2 with
  `hashicorp/kubernetes` 3.5.0 wrote neither key in CI, and a code search
  found them nowhere but in cub-scout and the code it was copied from.
- **`trace` JSON for Helm-installed objects changes.**
  - `answer.state` is `traced` where it was `readiness-not-read`, when Helm
    records the release as `deployed`; `chain-not-ready` for any other status.
  - Link roles change as above.
  - For an object named by Helm's annotations, `target` is the object, not
    the `Release`, and the chain has three links: chart, release, object.
- **kro owner names change** from an arbitrary label value to the instance's
  name. Where no label names the instance, the name is empty.
- **`explain` JSON may carry `mutationManagerTool`.**

## What was and was not verified

- **Real installs, in CI.** The GitOps lane installs each tool and asserts
  what cub-scout says about the objects it creates:
  - Flux v2.10.0 and Argo CD v3.6.1 ([#928](https://github.com/confighub/cub-scout/pull/928));
  - Helm 4.3.2 and 3.22.1, including two copied objects that must be credited
    to no release;
  - kro v0.10.0, Crossplane 2.4.3 and Terraform 1.17.2.

  The recorded kro object is also a unit-test fixture.
- **CI is pinned** ([#927](https://github.com/confighub/cub-scout/pull/927)):
  runner images, kind v0.31.0 with its node image by digest, and the release
  job's goreleaser at v2.20.2.
- **The live lane runs on Ubuntu 26.04**
  ([#934](https://github.com/confighub/cub-scout/pull/934)). 26.04 allows 128
  inotify instances where 24.04 allowed 1280. That is too few for the live
  lane's three kind clusters, so the lane raises the limits first.
- **The demo lane passes**
  ([#932](https://github.com/confighub/cub-scout/pull/932)). Its scanner
  demos were taken out on the maintainer's instruction: the repository has no
  credential to fetch the scanner (run 43869520475). The full lane still
  cannot provision it.
- **Independent review.** #929 and #933 were each read by a reviewer that did
  not write them. The review of #929 found a blocker, fixed before merge:
  copied annotations could credit an object to a release that did not install
  it.
- **Tests that fail without the fix.** Each code fix in #929, #933, #935,
  #936, #938, #940 and #942 has a test that fails without it. The CI changes
  are proven by the lanes themselves.
- **Not seen on a real install:** Modelplane, and Sveltos beyond the live lane.
- **Not measured:** no paid eval run was made. The `explain` and `trace`
  changes have no eval case, because paid runs are not approved.
