# v2.10.0 - Bounded Explorer Evidence

Previous release: v2.9.0. Publication, final artifact checks and any remaining
validation limitations are recorded in [#525](https://github.com/confighub/cub-scout/issues/525)
and the [release](https://github.com/confighub/cub-scout/releases/tag/v2.10.0).
This document describes the release scope; it is not a claim that an unfinished
publication or check has succeeded.

## What Changes

- Opt-in `explain --bounded` inspects one exact API object in an explicit kube
  context. A cold read uses at most one discovery document and one object GET,
  without controller commands, ConfigHub reads, object LISTs, or pod/event fan-out.
- CLI/plugin, MCP and the standalone TUI share `resourceRead`, object-local
  ownership/readiness, generation-aware workload evidence and explicit omissions.
- MCP and the standalone TUI reuse up to 16 observations for less than 15 seconds.
  Hits preserve timestamps and use zero discovery/object requests. Refresh,
  expiry and context/credential-configuration changes invalidate reuse. Failed
  refresh never returns old success; TUI navigation cancels pending work.
- The already-read `confighub.com/origin` annotation supplies optional observed
  source space/unit IDs, slugs and an exact integer revision. Missing, malformed,
  duplicate or conflicting metadata becomes an omission, not a guessed link.
- A separately released companion explorer adds Resource detail `3 Evidence`
  through the CLI JSON boundary. It requires an explicit Target-ID/context
  binding and retains one dated snapshot with a persistent stale indicator,
  zero-read tab revisits, explicit refresh and late-result rejection.

There is no breaking change to existing commands, JSON, MCP or receipt
contracts. The standalone TUI remains available. Watch and bot retain their
existing polling behavior; this release does not add a shared fleet cache.

## Try It

```sh
./cub-scout explain Deployment/api -n team-a --bounded \
  --api-version apps/v1 --kube-context my-test-context --format json
```

Installed plugin: `cub scout explain` with the same flags. Use `--kube-context`;
the host reserves `--context` for ConfigHub. For MCP, call `explain` with
`bounded: true`, `api_version`, `context`, `resource` and explicit namespace.
In the standalone map TUI, `Ctrl+e` opens the inventory-bound resource picker;
Enter reads, `r` refreshes, and Esc returns/cancels.

Examples and repeatable proofs: [bounded resource evidence](../../examples/bounded-resource-read/),
[bot](../../examples/bot/), and [companion evidence](https://github.com/confighub/cub-commander/blob/main/docs/resource-evidence.md).

## Compatibility And Upgrade Order

| Surface | Required version | Behavior |
|---|---|---|
| Standalone CLI and map TUI | Scout v2.10.0 | Bounded reads are opt-in; existing rich diagnostics remain unchanged. |
| `cub scout` plugin | Scout v2.10.0; actual host tested with `cub` v0.4.4 | Same provider and flags; independent invocations have independent caches. |
| MCP | Scout v2.10.0 | Restart the host's stdio server after upgrading to load the new provider. |
| Watch and bot | Scout v2.10.0 | Existing event/receipt semantics; no new bounded-session cache. |
| Companion Resource Evidence tab | Commander v0.3.0 and Scout v2.10.0 | Explicit binding; one captured snapshot, not Scout's MCP/TUI cache. |

Publish/install Scout first, then the companion. Scout v2.9.0 does not support
the bounded contract. An old or incompatible provider leaves the companion
panel unavailable; it never falls back to broader diagnostics or writes.

```sh
# Fresh plugin installs, pinned to compatible releases:
cub plugin install confighub/cub-scout@v2.10.0
cub plugin install confighub/cub-commander@v0.3.0
# Existing plugin installs:
cub plugin upgrade scout@v2.10.0
cub plugin upgrade commander@v0.3.0
cub scout version
cub commander --scout-binding '<target-id>=<kube-context>'
```

The companion also accepts `--scout-binary /absolute/path/to/cub-scout`; no
plugin replacement is required to use a standalone provider. Its existing
configuration-edit and rollout actions are separate from read-only evidence.

## Evidence Boundaries

- `resourceRead.available` means an identity-matching object was observed, not
  that delivery or application success was proved. Unavailable reads may exit
  successfully with omissions: inspect the field, not just the exit code.
- Source/controller evidence, related pods/events and desired/live comparison
  are deliberately omitted. Object-local readiness is not a delivery verdict.
- Origin is an observed annotation claim, not independently verified provenance,
  controller ownership or a release/target/component/variant join.
  It is added only to bounded explain surfaces, not rich explain/trace, map
  inventory, watch/bot events, receipts or connected joins.
- No Secret payloads or subresources. Successful response bodies are bounded to
  2 MiB, with a ten-second read timeout, no REST retries or HTTP redirects.
  Authentication-helper traffic is outside the discovery/object counters.
- Existing map inventory and ConfigHub browsing retain their own request costs.
  The companion snapshot may still be viewed after expiry with a `STALE` label;
  that does not revalidate credentials. Refresh performs a new provider read.

## Verification And Known Limits

The release gate covers full offline suites, repeated bounded/origin/context
and plugin/watch/bot contracts, race checks, read-only/doc guards, six-platform
Scout packaging, four-platform companion packaging, and non-production smoke.
The exact execution results, tested commits, CI jobs and published checksums
belong to [#525](https://github.com/confighub/cub-scout/issues/525).

Two pre-existing limitations were rechecked during preparation:

- Authenticated live ConfigHub proof is unavailable while the local login is
  expired. The companion's connected proof uses a synthetic intended-state
  endpoint plus a real existing Kubernetes object. That is not authenticated
  source-to-cluster mapping proof. User reauthentication and explicit test
  Target/context scope are required to complete that check.
- Anonymous pulls of the v2.9.0 registry image still returned HTTP 403; the
  anonymous token endpoint returned 401. Package permissions were not changed.
  [#520](https://github.com/confighub/cub-scout/issues/520) retains the distribution
  check; v2.10.0 is retried after publication. A successful container push or
  locally built image is not proof of public pull access.

These are explicit validation limitations, not passing checks. Archives and
local read-only container proof are verified independently. Do not recommend
the registry-based bot install as verified until the pull check succeeds.

The release container targets Linux amd64 only. Linux arm64 binaries are
included in the archives, but a local arm64 image built for the disposable
cluster smoke is not a published multi-architecture container. Loading the
amd64 image alone into that arm64 cluster did not start the bot.
