# v2.12.3 - Correct Owners in explain and trace, and MCP That Clients Can Reach

**Published: 2026-09-26.** Tag `v2.12.3` at `eec8da3`. Previous release: v2.12.2.
A patch release: no new commands, flags or JSON fields.

## User Value

Two fixes for agents, found while building the agent evals
([#603](https://github.com/confighub/cub-scout/issues/603)):

- **explain and trace report the right owner**
  ([#617](https://github.com/confighub/cub-scout/issues/617), #618). Both
  commands used to report the tracer that ran as the owner, even when that
  tracer had just answered "not managed by me". Unlabelled workloads came out
  as Helm in `explain` and Flux in `trace --format json`, ConfigHub-owned ones
  as Unknown or Flux, and custom-owned ones as Native in `trace`. The owner
  now comes from ownership detection, the classification `map list` uses. A
  tracer's tool is reported only when it produced a complete chain.
- **`cub-scout mcp serve` works with MCP clients** (#616). The server read
  only `Content-Length` framed messages, while the MCP stdio transport is
  newline-delimited JSON, so clients such as Claude Code timed out connecting.
  This has been the case since the server shipped in v1.7.0. It now accepts
  both framings and replies in the framing of each request.

Checked on a kind cluster with six Deployments whose ownership is given only
by labels, with the `flux`, `argocd` and `helm` CLIs installed:

| Deployment | `map list` | `explain` owner, v2.12.2 → v2.12.3 | `trace --format json` ownerType, v2.12.2 → v2.12.3 |
|---|---|---|---|
| no GitOps labels | Native | Helm → Native | Flux → Native |
| `confighub.com/UnitSlug` | ConfigHub | Unknown → ConfigHub | Flux → ConfigHub |
| Flux kustomize labels | Flux | Flux → Flux | Flux → Flux |
| Helm labels | Helm | Helm → Helm | Helm → Helm |
| Argo instance + tracking-id | ArgoCD | ArgoCD → ArgoCD | tracer error (no Argo server), unchanged |

Claude Code 2.1.281's MCP client, pointed at `cub-scout mcp serve`: v2.12.2
`Connection failed after 28017ms (CONNECT_TIMEOUT)`; this release
`Successfully connected (transport: stdio) in 1117ms`, with its tools listed.

Also on `main` since v2.12.2:

- #615: every skill's `allowed-tools` grant is read-only however the command
  line is completed. Six grant patterns admitted a write or an outbound send
  (for example `import --dry-run *` admitted `--dry-run=false`), and a test now
  checks every grant against the command tree.
- #613, #614: published v2.12.2 references and the planned remaining 2.x
  releases.

## Limits

- `trace` still exits 1 for a resource no GitOps tool manages, as the CLI
  contract says, and MCP tools still return only the exit status when a
  command exits non-zero, so an agent calling the MCP `trace` tool on such a
  resource gets no JSON
  ([#619](https://github.com/confighub/cub-scout/issues/619)).
- `explain` reports `health: "Unavailable"` when the trace has no chain. Per
  the JSON contract that means health was not measured, not that the workload
  is down ([#620](https://github.com/confighub/cub-scout/issues/620)).
- When ownership detection cannot read the object, `explain` and `trace`
  behave as before.
- v2.12.2's limits still apply.
