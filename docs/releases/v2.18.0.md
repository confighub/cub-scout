# v2.18.0 — Answers an agent can act on, and writes that name their cluster

The release before it is [v2.17.0](v2.17.0.md).

Seven more commands now carry the `answer` block that `trace` and
`compare source-truth` gained in v2.16.0: `gitops status`, `explain`,
`doctor`, `map list`, `scan`, `gitops settings` and `release check`. Each
says, in one closed list of state words per command, what the command found,
whose word each fact rests on, what it could not establish, and what its reads
cost.

Every cluster write cub-scout makes (the demos, `import argocd`'s sync and
delete, the import wizard's Argo CD hand-off and `map hub`'s import) now
refuses unless the cluster is named with `--kube-context`. Every command takes
that flag, or a registry test records why it reads no cluster. Reads without
the flag still use the current context, as before.

Read [Behaviour changes to expect](#behaviour-changes-to-expect) before
upgrading if you run the demos, use `import argocd --disable-sync` or
`--delete-app`, use `map hub`'s import, or parse `gitops status` text.

## Added

- **The answer block on seven more commands.** Each is a top-level `answer`
  beside the command's existing JSON, which is unchanged. The fields are
  `state`, `reason`, `summary`, `observedAt`, `cluster`, `basis[]`,
  `unknowns[]`, `next[]` and `cost`, as in
  [the proposal](../proposals/answer-envelope.md). The state words were decided
  by the maintainer on 2026-11-19; each command's table is in
  [json-contracts.md](../reference/json-contracts.md).

  | Command | States |
  |---|---|
  | `gitops status` ([#965](https://github.com/confighub/cub-scout/pull/965)) | `settled`, `converging`, `failing`, `no-deployers`, `not-observable` |
  | `explain` ([#966](https://github.com/confighub/cub-scout/pull/966), [#968](https://github.com/confighub/cub-scout/pull/968)) | `explained`, `owner-only`, `no-owner-marker`, `not-observable` |
  | `doctor` ([#967](https://github.com/confighub/cub-scout/pull/967), [#969](https://github.com/confighub/cub-scout/pull/969)) | `issues-flagged`, `nothing-flagged`, `incomplete`, `not-observable` |
  | `map list --summary` and `--cluster-identity` ([#972](https://github.com/confighub/cub-scout/pull/972)) | `listed`, `partial`, `not-observable` |
  | `scan --json` and `--normalized-json` ([#973](https://github.com/confighub/cub-scout/pull/973)) | `findings`, `no-findings`, `incomplete`, `not-observable` |
  | `gitops settings --format json` ([#974](https://github.com/confighub/cub-scout/pull/974)) | `listed`, `no-deployers`, `partial`, `not-observable` |
  | `release check --format json` ([#975](https://github.com/confighub/cub-scout/pull/975)) | `matches`, `differs`, `not-compared`, `not-observable` |

  - No state is a health claim. `nothing-flagged` and `no-findings` list what
    was not checked in `unknowns`, and `release check`'s `matches` keeps the
    report's omissions, such as application success.
  - "Not yet" differs from "no": `converging` from `failing`, `incomplete` from
    `nothing-flagged`, `not-compared` from `differs`.
  - Text from the cluster (finding messages, controller reasons, errors) is
    quoted in `basis` or `unknowns`, never in `summary`; `next` commands are
    built only from names that pass a strict pattern.
  - The MCP tools carry the same answer, unchanged, in their text and in
    `structuredContent`; a test holds each one to the CLI's.
  - `cost` counts the command's own in-process Kubernetes requests, under a
    named `coverage` key. Subprocesses, ConfigHub reads and registry reads are
    not counted. Recorded input carries no answer, or `not-measured` cost.
- **`doctor --before-attach`**
  ([#947](https://github.com/confighub/cub-scout/pull/947),
  [#952](https://github.com/confighub/cub-scout/pull/952)). What
  `cub cluster attach` would meet in this cluster, for each of Argo CD, Flux
  and Sveltos: `refuse`, `use-existing`, `install` or `unknown`, each naming
  the object it rests on. It was designed from recordings of real attaches in a
  new manually dispatched CI lane. It reads Secrets by metadata only, never
  attaches, and never says a cluster is safe to attach.
- **Every command takes `--kube-context` or says why not**
  ([#953](https://github.com/confighub/cub-scout/pull/953),
  [#954](https://github.com/confighub/cub-scout/pull/954),
  [#956](https://github.com/confighub/cub-scout/pull/956)–[#960](https://github.com/confighub/cub-scout/pull/960),
  [#964](https://github.com/confighub/cub-scout/pull/964)). A registry test
  fails when a command reads a cluster with neither the flag nor a stated
  reason. This release adds the flag to `suggest-remedy`, the demos,
  `quickstart`, `import argocd`, `views project --with-reality`, `import`, the
  import wizard and `map hub`. No command now reads through the current
  context without offering the flag.

## Changed

- **Writes need a named cluster**
  ([#962](https://github.com/confighub/cub-scout/pull/962),
  [#964](https://github.com/confighub/cub-scout/pull/964)). A maintainer
  decision: reads may default to the current context; writes may not.
  - The demos (`quickstart demo`, `quickstart demo scenario`, and the hidden
    `demo`) refuse without `--kube-context`, before any `kubectl` call. Their
    fixtures use namespaces such as `production`, `argocd` and `flux-system`,
    and `--cleanup` deletes by name.
  - `import argocd --disable-sync` and `--delete-app`, and the import wizard's
    Argo CD hand-off, refuse without it. `--dry-run` and `--show-yaml` do not.
  - `map hub`'s writes (Argo CD sync and Application changes, workload label and
    annotation changes) refuse without it, and its imports stop before creating
    any ConfigHub unit.
  - The read-only guard (`scripts/check-readonly.sh`) now also fails on a
    `kubectl` write verb run as a subprocess outside the files allowed to write.
- **`trace` reads a Crossplane composite's `Ready` as Crossplane's report**
  ([#963](https://github.com/confighub/cub-scout/pull/963)). A link carrying
  `crossplane.io/composite` with a `Ready` condition is read as
  `controller-report`. A not-ready one gives `chain-not-ready` where the answer
  was `readiness-not-read`. This covers Modelplane objects, which Crossplane
  composes.
- **Human output follows the answer**
  ([#949](https://github.com/confighub/cub-scout/pull/949),
  [#971](https://github.com/confighub/cub-scout/pull/971)). `trace` text,
  Markdown and TUI say "All levels in sync" only when the answer is `traced`.
  The `gitops status` headline says healthy only when the answer is `settled`
  with nothing suspended, and failing only when it is `failing`; otherwise it
  prints the answer's sentence.
- **Unit events are no longer read**
  ([#946](https://github.com/confighub/cub-scout/pull/946)). ConfigHub no
  longer records them. Their JSON fields and the `confighub_unit_events` MCP
  tool remain, always empty. SDK core moves to v0.11.9.

## Deprecated

- **Everything 3.0 removes now says so**
  ([#950](https://github.com/confighub/cub-scout/pull/950)), on stderr:
  `fleet outliers`, `gitops status --json`, `trace --json`, `tree --json`,
  `graph export --json`, `connect --go`, `app create --set-context` and
  `hierarchy`. JSON on stdout is unchanged. Each `--json` flag's replacement is
`--format json`. The deprecation window starts with
  this release. [The migration guide](../migration-3.0.md) lists each
  replacement.

## Behaviour changes to expect

- **Demos, `import argocd --disable-sync`/`--delete-app`, the wizard's Argo CD
  hand-off and `map hub`'s writes fail without `--kube-context`**, with a
  message naming the flag. Use a disposable cluster for the demos
  (`kind create cluster --name demo`).
- **Reads are unchanged without `--kube-context`.** `import`,
  `views project --with-reality`, `quickstart`, `suggest-remedy --all` and the
  others that gained the flag read the current context when it is not given.
- **JSON gains a top-level `answer`** on the seven commands above. No existing
  field moves. `map list`'s default array and `--ownership-evidence` form carry
  none.
- **`trace` JSON for Crossplane-composed objects** may read `chain-not-ready`
  where it read `readiness-not-read`.
- **`gitops status` text** prints the answer's sentence where it printed
  "All N deployers healthy" or "N/M deployers failing" for an unread,
  progressing or suspended deployer.
- **Deprecation notices on stderr** for the commands and flags above.

## What was and was not verified

- **Real clusters, in CI.** The GitOps lane runs real Flux and Argo CD on kind
  and checks each answer on the boutique example. On the PR runs:
  `gitops status` `settled` (5 deployers, 38 requests), `explain`
  `explained` (3 links), `doctor` `nothing-flagged` (17 resources),
  `map list` `listed` (17 resources), `scan` `no-findings` (12 requests) and
  `gitops settings` `listed` (5 deployers, 3 requests). The Modelplane lane recorded `trace` on a real
  ModelDeployment as `chain-not-ready`. The attach lane recorded real
  `cub cluster attach` runs for Argo CD, Flux and Sveltos.
- **`release check`'s answer** has no real-cluster check: no lane runs
  `release check`. Its test drives the real command against a fake API.
- **Tests that fail without the change.** Each answer has a mutation check
  against its state precedence and, where it meters, against its meter.
- **Not measured:** no paid eval run was made, so whether the answer blocks
  save an agent turns or cost is not yet shown.
