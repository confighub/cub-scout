# Onboard Existing: Pattern 1 Takeover for Argo and Flux

> **Status:** This describes a planned v1 flow. The `cub-scout onboard`
> command is specified in [docs/specs/pattern-1-takeover-v1.md](../specs/pattern-1-takeover-v1.md)
> and is not yet shipping. See [docs/roadmap.md](../roadmap.md) for current
> milestone state.

This guide walks you through bringing an existing Argo CD Application or
Flux Kustomization under ConfigHub governance without redeploying your
workloads. Your controller keeps running; its source moves from Git to
ConfigHub OCI.

If you only want to register existing workloads in ConfigHub for
visibility (without touching the controller's source), see
[Import to ConfigHub](import-to-confighub.md). This document is the
takeover flow that picks up from there.

## What Pattern 1 Is

Pattern 1 is the takeover style where:

- ConfigHub becomes the source of truth and OCI publisher.
- The customer's existing Argo or Flux controller keeps reconciling.
- The controller's `spec.source` (Argo) or `spec.sourceRef` (Flux) is
  updated to point at ConfigHub OCI.
- The cluster shape does not change at takeover. The same workloads
  keep running, now governed.

Pattern 2 (write-through-Git, where ConfigHub publishes back to Git) is
out of v1 scope. If your audit policy requires Git as system-of-record,
Pattern 1 is not the right path; track the v2 plan instead.

## When to Use This

Use this when:

- You have running Argo CD or Flux.
- You want changes reviewed and applied through ConfigHub instead of
  Git PRs.
- You can change the controller's source spec from Git to OCI.
- You can pull from ConfigHub OCI from inside the cluster (network and
  auth path).

Do not use this when:

- You require Git as the immutable source-of-record (audit / policy
  reasons). Use Pattern 2 when that ships.
- Your Argo Applications are generated by an active ApplicationSet that
  you cannot pause. Generator takeover is v2; v1 supports
  generated-children takeover with caveats.
- Your Flux HelmRelease pulls from a non-OCI HelmRepository. v1 supports
  OCI-capable sources only.

## Prerequisites

```bash
# Auth
cub auth login

# Verify cluster access from your shell (cub-scout is read-only at the
# cluster; the takeover writes happen through cub)
kubectl cluster-info

# Verify the controller is reachable
kubectl -n argocd get application      # Argo
kubectl -n flux-system get kustomization  # Flux

# Verify OCI auth from inside the cluster
# (the controller's ServiceAccount needs to be able to pull from
# ConfigHub OCI). Coordinate with your platform team.
```

## The Flow

### Step 1 — Discover and propose

Run the dry-run first. This is read-only on both the cluster and
ConfigHub.

**Argo:**

```bash
cub-scout onboard --controller argo -n <namespace> --dry-run
```

**Flux:**

```bash
cub-scout onboard --controller flux -n <namespace> --dry-run
```

Output covers:

- the Application(s) or Kustomization(s) found and their current source
  (Git URL, path, ref);
- the proposed Component / Base Variant / Deployable Variant in
  ConfigHub;
- the predicted OCI render vs the controller's current Git render
  (the *render diff*);
- the draft Connections (discovered Secrets, ConfigMaps, etc.);
- whether the takeover is byte-equivalent, cosmetically different, or
  semantically different.

The render diff is the key new thing. It tells you exactly what the
controller will see at takeover.

### Step 2 — Resolve the render diff

Three outcomes:

| Outcome | Meaning | Action |
|---------|---------|--------|
| **Byte-equivalent** | OCI render is identical to the controller's current render. | Proceed. No reconcile churn at takeover. |
| **Cosmetic only** | Field ordering or whitespace differs; semantics identical. | Inspect the diff. Pass `--accept-cosmetic-diff` to proceed. The controller will see one no-op apply at takeover. |
| **Semantic difference** | Resource bodies, replicas, env values, or images differ. | Stop. Your Git source and your proposed Component are not yet aligned. Fix the divergence (usually in the Component) before retrying. |

If the dry-run shows a semantic diff, treat it as an engineering loop,
not a takeover. Do not try to bypass it.

### Step 3 — Take over

Once the diff is acceptable:

```bash
# Argo
cub-scout onboard --controller argo -n <namespace> [--accept-cosmetic-diff]

# Flux
cub-scout onboard --controller flux -n <namespace> [--accept-cosmetic-diff]
```

Sequence of operations:

1. ConfigHub state is created (Component, Base Variant, Deployable
   Variant) via `cub`.
2. The first OCI artifact is published.
3. The Argo Application's `spec.source` (or the Flux Kustomization's
   `spec.sourceRef`) is updated to point at ConfigHub OCI. This is the
   one cluster-mutating step.
4. cub-scout waits for the controller to reconcile (default 5 min).
5. cub-scout runs `compare three-way` and reports the result.

### Step 4 — Verify

```bash
cub-scout compare three-way --scope namespace/<namespace>
```

All three layers should match: intent (ConfigHub Variant), render
(ConfigHub OCI), observed (cluster).

The takeover writes a proof record to the audit log:

```bash
cub-scout audit list -n <namespace> --since 1h
```

The record includes the pre-takeover Git ref, the post-takeover OCI
URL, the render diff outcome, and the verification result. This is
the four-layer proof, made repeatable.

### Step 5 — Apply a change

After takeover, changes flow through ConfigHub. The controller pulls
from OCI and reconciles. Verify each change with three-way compare:

```bash
# Apply your change through cub or the ConfigHub UI
cub unit update <unit-slug> --space <variant-space-slug> ...

# Wait for the controller to reconcile, then verify
cub-scout compare three-way --scope namespace/<namespace>
```

## Argo CD Specifics

### Single Application

`spec.source` is updated from a Git source to an OCI source. Argo CD
2.6+ supports OCI sources natively.

### App-of-Apps / ApplicationSet

The parent App or ApplicationSet generates child Applications
dynamically. v1 takeover applies to the *generated children*, not to
the parent generator.

Caveat: an active ApplicationSet will keep generating Git-sourced
children, fighting the takeover on its next sync. Mitigations:

- pause the ApplicationSet during validation;
- migrate ApplicationSet generators to point at OCI templates (manual
  for v1);
- track v2 for first-class generator takeover.

## Flux Specifics

### Kustomization with GitRepository source

The Kustomization's `spec.sourceRef` is changed from a `GitRepository`
to an `OCIRepository`. The `OCIRepository` resource is created in the
same namespace, pointing at ConfigHub OCI. Flux 2.0+ supports
`OCIRepository` as a first-class source.

### HelmRelease with OCI HelmRepository

Supported. The HelmRepository is repointed at ConfigHub's OCI registry.

### HelmRelease with non-OCI HelmRepository

Not supported in v1. The HelmRepository itself would have to be
migrated to OCI, which is beyond a sourceRef swap. Track this as a v2
gap.

## Rollback

If the takeover went wrong:

```bash
cub-scout onboard --rollback --controller argo -n <namespace>
```

This restores the pre-takeover Git ref on the Argo Application (or the
Flux Kustomization), referencing the audit record from Step 4.

**Important:** Rollback is safe *if* you have not applied changes
through ConfigHub since takeover. If you have:

- Those changes exist in ConfigHub but not in Git.
- Rollback to Git loses them.
- cub-scout warns and refuses `--rollback` without
  `--accept-data-loss`.

If you've made changes through ConfigHub and need to roll back without
losing them, that's Pattern 2 (write-through-Git). Out of v1 scope.

## Graceful Degradation

| Scenario | Behavior |
|----------|----------|
| Controller unreachable | Discovery fails fast with remediation. No partial takeover. |
| Render diff is semantic | Command stops, shows the diff, exits non-zero. No mutation. |
| OCI publish fails | Rollback to pre-publish state. Cluster untouched. |
| Source repoint fails | Rollback to pre-repoint state. ConfigHub state retained for retry. |
| Reconcile timeout | Takeover marked "applied, unverified." Operator runs `compare three-way` manually. |
