# GitOps hierarchies

GitOps systems are hierarchical.

Controllers create other controllers and workloads, forming ownership and
reconciliation chains that explain *why* resources exist.

cub-scout’s core value is making these hierarchies:

- visible
- explainable
- deterministic
- provable

This document explains how cub-scout models GitOps hierarchies across tools,
with concrete examples.

---

## The invariant (tool-agnostic)

Across GitOps tools, the same structural truth applies:

> **GitOps resources compose into applications, and applications are often
> built from other GitOps resources.**

Examples:
- A Flux application composed of multiple Kustomizations and HelmReleases
- An Argo CD Application generated by an ApplicationSet
- A parent Application applying child Applications (App-of-Apps)

cub-scout does not invent new abstractions for this.
It exposes the hierarchy that already exists.

---

## Flux: explicit reconciliation chains

Flux models hierarchy directly.

A typical Flux chain looks like:

```
GitRepository
└─ Kustomization
   ├─ HelmRelease
   └─ Kustomization (nested)
```

### How cub-scout shows this

- **Tree** shows the full hierarchy, grouped and ordered deterministically
- **Trace** narrates the reconciliation chain:
  *this Deployment exists because this HelmRelease was reconciled by this
  Kustomization, sourced from this GitRepository*

Flux is the “clean” case — the hierarchy is explicit and first-class.

---

## Argo CD: emergent hierarchies

Argo CD does not yet support explicit dependency modeling (such as `dependsOn`).

As a result, teams model hierarchy indirectly using:

- **ApplicationSets** (generators that create Applications)
- **App-of-Apps** patterns (Applications applying other Applications)
- **Mixed hierarchies** combining both patterns

These structures are powerful — and often hard to reason about.

cub-scout reconstructs these hierarchies from live cluster state.

---

## What users are really asking for

This feedback captures the core problem:

> “An application could be made up of many GitOps resources
> (Kustomizations, HelmReleases, etc.).
>
> Since Argo CD doesn’t have dependsOn yet, many users are doing App-of-Apps or
> ApplicationSets. Some end up with App-of-AppSets-of-App-of-Apps.
>
> It would be great to clearly see those relationships for issue triage.”

There are two needs here:

1. **Composition**  
   Multiple GitOps resources form a single operational application.

2. **Meta-hierarchies**  
   Controllers create other controllers, not just workloads.

cub-scout addresses both using tree and trace.

---

## Tree: making hierarchy explicit

Tree is cub-scout’s primary surface.

It answers:
- *What exists?*
- *How is it grouped?*
- *Who owns it?*

### Example: Argo CD meta-hierarchy

```
namespace/platform
└─ Application/platform
   └─ ApplicationSet/workloads
      ├─ Application/app-a
      │  └─ Deployment/app-a
      ├─ Application/app-b
      │  └─ Deployment/app-b
      └─ Application/app-c
         └─ Deployment/app-c
```

Tree makes visible:
- parent/child Application relationships
- Applications generated by an ApplicationSet
- the full scope of an “application” composed of many resources

No guessing. No flattening.

---

## Trace: telling the creation story

Trace answers a different question:

> *Why does this exist?*

It narrates the controller chain that led to a resource.

### ApplicationSet trace

```
ApplicationSet/workloads
└─ generates Application/app-a
   └─ syncs Deployment/app-a
```

### App-of-Apps trace

```
Application/platform
└─ applies Application/app-a
   └─ syncs Deployment/app-a
```

### Mixed hierarchy trace

```
Application/platform
└─ applies ApplicationSet/workloads
   └─ generates Application/app-a
      └─ syncs Deployment/app-a
```

Trace is deterministic, ASCII-first, and explicitly labels each relationship
using plain language (“applies”, “generates”, “syncs”).

---

## Why this helps with triage

When something breaks, operators often ask:

- Why does this Application exist?
- Who created it?
- Is it safe to delete?
- What else depends on it?

cub-scout answers these questions by:

- making hierarchy visible (tree)
- proving the creation chain (trace)

This is especially valuable in large Argo CD environments where
meta-hierarchies evolve organically over time.
