# cub-scout v0.5 Review Strategy

This document defines how code review works for v0.5 when operating with
a solo human + agents model.

Review is replaced with **automated gates + structured agent review + runtime verification**.

---

## Core Principle

You don't skip review. You replace human code review with:

1. **Objective CI gates** (pass/fail signals you can trust)
2. **Behavioral proof** (evidence from real clusters)
3. **Two-agent separation** (author ≠ reviewer)

---

## CI as Primary Reviewer

Merges are impossible unless objective gates pass.

### Required Gates (Every PR)

| Gate | Purpose | Status |
|------|---------|--------|
| `go test ./...` | Unit tests pass | ✅ Exists |
| `golangci-lint` | Static analysis | ✅ Exists |
| `govulncheck ./...` | Go vulnerability scanning | 🔧 To add |
| Build artifact | Compiles for supported targets | ✅ Exists |
| Read-only policy | No write operations | ✅ Exists |
| Integration tests | Basic cluster commands work | ✅ Exists |
| GitOps E2E | Flux + ArgoCD ownership detection | ✅ Exists |

### Semantic Gates (v0.5 additions)

| Gate | Purpose | Status |
|------|---------|--------|
| Golden tests: ownership | Snapshot-based ownership output | 🔧 To add |
| Golden tests: failure/health | Snapshot-based health classification | 🔧 To add |
| Contract tests: `--json` | Schema stability for machine output | 🔧 To add |

### Review Becomes

> "Does this PR change any golden outputs? If yes, it must be explained and approved."

That's manageable without reading code.

---

## Cluster Proof Requirement

For PRs touching risky areas, require **evidence, not eyeballs**.

### Risky Areas

- Ownership/provenance logic
- Failure/health modeling
- TUI core flows

### Required Evidence

1. Short log or captured output from real cluster
2. Commands used
3. Observed before/after behavior
4. Screenshots (for TUI changes)

This is review by **behavioral proof**.

---

## Two-Agent Rule

The same agent MUST NOT author and approve.

### Roles

| Agent | Responsibility |
|-------|----------------|
| Claude | Implements PR, posts evidence |
| Codex | Reviews behaviorally, decides merge/reject |

### PR Requirements

Claude posts in every PR description:

1. What changed
2. Why
3. Tests added
4. Golden diffs (if any)
5. Cluster proof (for risky areas)

### Review Decision

Codex reviews based on:

- Diff summary
- Test changes
- Golden output diffs
- Cluster proof artifacts

Decision: **merge** or **reject** with reason.

---

## Review Cadence

### Every PR (Non-Negotiable)

- CI gates pass
- Golden diffs explained (if any)
- Cluster proof provided (for risky areas)
- Agent separation maintained

### Weekly

Integration sweep on 2 clusters:

- One Flux-heavy
- One ArgoCD-heavy (if available)

Any mismatch becomes a v0.5 bug or waiver issue.

### Per Release Candidate

- Full v0.5 checklist pass
- Waiver review
- Clean room run: fresh install, fresh cluster, docs exactly as written

### Quarterly (Post-v0.5)

- Dependency posture review
- Permissions review (kube access needed)
- Threat model refresh

## Golden Test Strategy

### What Gets Golden Tests

| Area | Test Type | Location |
|------|-----------|----------|
| Ownership detection | Snapshot comparison | `test/golden/ownership/` |
| Failure classification | Snapshot comparison | `test/golden/health/` |
| JSON output schema | Contract test | `test/golden/schema/` |

### How Golden Tests Work

1. Test runs cub-scout against fixture manifests
2. Output is compared to stored golden file
3. Any diff fails the test
4. To update: `go test ./... -update-golden`

### Updating Golden Files

Golden file changes require:

1. Explanation in PR description
2. Verification that change is intentional
3. Codex approval

## Long-Term Strategy

### Reduce Surface Area Needing Review

- Keep ownership rules explicit, conservative, test-locked
- Freeze CLI JSON schemas early
- Prefer "unknown" states over brittle heuristics

### Build Trust Rails

- Golden tests = change detector
- Fuzz/property tests for parsers
- "No panic" policy enforced by tests

### External Review at Milestones

- Before 1.0: One external security/code audit
- Before connected-mode: Threat model + privacy review

### Operational Controls

- Branch protections prevent gate bypass
- Minimize GitHub token permissions for agents
- Signed releases when distributing widely
